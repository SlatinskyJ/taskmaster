# Bidding on one-time tasks: server (PR A of 2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task (CLAUDE.md, PR flow step 3). Steps use checkbox (`- [ ]`) syntax for tracking.

**Issue:** [#34 Bidding on one-time tasks](https://github.com/SlatinskyJ/taskmaster/issues/34), part 1 of 2. This PR does not close it; PR B (the screens, stacked on this one, own plan) does.

**Depends on:** [#133 Spec: a bidder who says yes picks his or open for both](https://github.com/SlatinskyJ/taskmaster/pull/133) (Jakub's decision of 2026-11-18, one sentence in §5.2). Merge #133 first. This PR does not edit the spec.

**Goal:** The server side of bidding: a taker counters a giver's offer on a one-time task, the two sides go back and forth until one accepts, which reserves the task to that taker (or opens it on a tie), every bid and counter is kept, and the views carry what a screen needs to show it.

**Architecture:** The rules already exist in `src/domain/bidding.ts` (#20); two of them get stricter (Task 3). This PR stores the negotiation as one append-mostly table, `task_thread` (giver-side offers and takers' bids), adds four server actions that load the rows, ask the domain and write the result with its audit entries in one transaction, the reads a screen needs, six guarded server functions, and demo data. No screen changes: the existing "Souhlasím" flow keeps working unchanged.

**Tech Stack:** TanStack Start server functions, Drizzle + better-sqlite3 (sync transactions), Vitest.

**Spec:** `docs/superpowers/specs/2026-11-16-taskmaster-design.md` §5.2 (path 2 and Details, except "Changing the score of an agreed one-time task", which is #36), §3 (score agreement, [call] any active giver), §5.4 (release of a bid-agreed task: its new offer joins the thread), §5.10 (audit).

## What exists already

- `src/server/tasks/tasks.ts`: `createTask`, `approveTaskOffer` (path 1), `reopenOffer` (release of a bid-won task), `resolveProposedTasks` (people-change hook). Today `agreementOf` passes the domain an empty bid book and takes the task's creator as the offering giver; this PR feeds it the real thread.
- `tasks` already has `offer_round`, `reserved_via` (`tap` | `bid`) and `reserved_giver_id`.

## Decisions this plan makes

1. **One table, `task_thread`, holds the negotiation.** It is not called "bids" because the giver side does not bid (`src/domain/bids.ts`); it offers. A row is a giver-side offer (`side = 'giver'`: the first offer, a counter, the re-offer after a release) or a taker's bid (`side = 'taker'`). A row is open until it closes as `replaced` (the same side put a new number), `accepted` (the task was agreed at it) or `closed` (the task was agreed at something else). While a task is `proposed` it has exactly one open giver row (the current offer; its `score` equals `tasks.score`, its `user_id` is the offering giver) and at most one open row per taker. Two partial unique indexes enforce both. Rows are never deleted, so every bid and counter stays in the history (spec §5.2). The current offer is stored twice (`tasks.score` and the open giver row): the only writers of a giver row are `createTask`, `counterOffer` and `reopenOffer`, each of which writes both in one transaction. The schema comment names them, and the tests for those three check `offerInStep(db, id)` (open giver row's score equals `tasks.score`).
2. **Audit actions.** A taker's bid: new `task.bid_placed`. A giver's counter: existing `task.score_countered`. A taker accepting the offer: existing `task.score_approved` then `task.agreed`. A giver accepting the lowest bid: new `task.bid_accepted` then `task.agreed`. All on entity `task`, so #36's task history gets them. `task.agreed` now always says which thread rows it closed: `after.accepted` (ids closed as `accepted`) and `after.closed` (ids closed as `closed`).
3. **An accepted bid starts a new offer round** (`offer_round + 1`, no approval rows in it): the agreed score is not the number the old round's approvals were given for, so none of them sits on it (spec §5.2 "pending score approvals are discarded").
4. **The views carry what PR B shows.** `TaskView` gains the offering giver, open bids, the lowest bid with its holders, and `approverIds` (ids of who approved the current offer, so a screen can tell a taker he already agreed); `getTaskDetail` returns the task with its whole thread (each entry with its instant). Screens come in PR B.
5. **One place writes a task's state.** `saveItem` (`src/server/tasks/item.ts`) is used by every lifecycle step and by every agreement. It closes the thread whenever a task leaves `proposed`, so a later step that does so (cancel, #36) cannot leave open offers or bids behind.
6. **Two stacked PRs** (Architecture judge, plan round 1). See Size.
7. **A bidder's yes picks** (Jakub, 2026-11-18, spec PR #133): a taker with an open bid may approve the offer (path 1, `approveTaskOffer`: the task opens for every taker, his bid closes) or accept it (`acceptOffer`: reserved to him). A taker without a bid has path 1 only (`acceptOffer` refuses `no_bid`). The domain from #20 already allows both (pinned by the domain test "a brother approving the plain offer while others bid opens it for everyone"); this PR adds server tests for both.
8. **A giver's counter** (Jakub, 2026-11-18, decision cards after Rules plan round 1; the two sentences go into spec PR #133): (a) a giver may change the offer any time while the task is proposed, with or without bids (a new offer round, so earlier approvals of the old number no longer count); (b) a counter at exactly a taker's open bid **accepts that bid**: reserved to that taker with the countering giver, or open at that number when several takers bid it (the tie rule). This holds for any open bid, not only the lowest. `counterOneTimeOffer` (domain) returns the agreed result in case (b); `counterOffer` (server) then ends the negotiation like `acceptLowestTaskBid` (`task.bid_accepted`, then `task.agreed`, new offer round). Template score changes (`scoreChange.ts`) are not touched here: [#141 Template score change: does a giver's counter at a bid's number accept it?](https://github.com/SlatinskyJ/taskmaster/issues/141) asks whether they follow (b) too.
9. **Names.** The server action that accepts the lowest bid is `acceptLowestTaskBid` (like `approveTaskOffer`), so it does not clash with the domain's `acceptLowestBid` (Architecture nit).

## Global Constraints

- Scores are whole numbers from 1 (spec §3). No upper limit on the server.
- Every state change writes its audit entry in the same transaction (`writeAudit(tx, …)`), and the check and the write share that transaction.
- An accept carries what the person saw and is refused when it changed (`offer_changed`): the offer for a taker; the lowest bid and who holds it for a giver's accept; the takers at that number for a giver's counter.
- Code, DB and audit names in English.
- Stored instants are UTC via `toIsoUtc(now)`; tests use fixed instants, never `new Date()`.
- No import of React, TanStack, DB or Node into `src/domain/`.
- Never edit a committed migration; `drizzle/` generated files stay byte-identical to drizzle-kit's output (the data step is its own custom migration).
- Nobody becomes inactive part-way (Jakub, 2026-11-17): no new handling or tests for a deactivated bidder beyond the domain's existing live filter.

## Review Focus

Each line has its test in the task named.

1. A taker accepts on a stale screen after the giver gave the task to his brother → refused, nothing written, the detail shows the brother's reservation (Task 3 "first agreement wins", Task 4 detail of a lost task).
2. The giver accepts "22 (Mladší)" while the bids move → refused with `offer_changed` when the lowest score changed, when another taker now holds it, or when it became a tie; never a winner or a price he did not see (Task 3, domain and server).
3. A bid-won task is released and negotiated again → bids from the first negotiation must not count as open (Task 3 "released and negotiated again").
4. Tasks created before this migration have no thread rows → each gets its first offer by the data migration, or approving them would throw (Task 1).
5. A double tap sends the same bid twice → the second is `same_score`, one open bid remains; the unique index backs it (Task 1, Task 3).
6. A bidder approves the offer → the task opens for everyone, not reserved to him; accepting it reserves it to him (Task 3 "a bidder's yes picks").
7. A giver counters with a bid's own number → agreed with that taker (or open on a tie), the whole thread closed, a new offer round; a counter with nobody bidding is a plain new offer (Task 3, decision 8).

```ts
export const THREAD_SIDES = ['giver', 'taker'] as const
export const THREAD_CLOSINGS = ['replaced', 'accepted', 'closed'] as const

export const taskThread = sqliteTable(
  'task_thread',
  {
    id: integer('id').primaryKey({ autoIncrement: true }),
    taskId: integer('task_id').notNull().references(() => tasks.id),
    /** Who put the number: the offering giver, or the bidding taker. */
    userId: integer('user_id').notNull().references(() => users.id),
    side: text('side', { enum: THREAD_SIDES }).notNull(),
    score: integer('score').notNull(),
    createdAt: text('created_at').notNull(),
    /** Null while open. */
    closedAt: text('closed_at'),
    closedAs: text('closed_as', { enum: THREAD_CLOSINGS }),
  },
  (t) => [
    check('task_thread_side_check', sql`${t.side} IN ('giver', 'taker')`),
    check('task_thread_score_check', sql`${t.score} >= 1`),
    check(
      'task_thread_closed_check',
      sql`(${t.closedAt} IS NULL AND ${t.closedAs} IS NULL) OR (${t.closedAt} IS NOT NULL AND ${t.closedAs} IN ('replaced', 'accepted', 'closed'))`,
    ),
    uniqueIndex('task_thread_open_offer_idx').on(t.taskId).where(sql`closed_at IS NULL AND side = 'giver'`),
    uniqueIndex('task_thread_open_bid_idx').on(t.taskId, t.userId).where(sql`closed_at IS NULL AND side = 'taker'`),
    index('task_thread_task_idx').on(t.taskId),
  ],
)
export type ThreadRow = typeof taskThread.$inferSelect
```

**Interfaces:**
- Consumes: `taskThread`, `ThreadRow` (Task 1).
- Produces, `thread.ts`:
  - `addEntry(tx: Tx, entry: { taskId: number; userId: number; side: 'giver' | 'taker'; score: number }, now: Date): { entry: ThreadRow; replaced: ThreadRow | null }` closes as `replaced` the open row it supersedes (giver side: the task's open offer; taker side: that taker's open bid), then inserts.
  - `openOffer(db: Db | Tx, taskId: number): ThreadRow` throws `task <id> proposed without an open offer` when there is none.
  - `openBids(db: Db | Tx, taskId: number): ThreadRow[]` open taker rows, by id.
  - `closeThread(tx: Tx, taskId: number, accepted: readonly number[], now: Date): { accepted: number[]; closed: number[] }` closes every open row of the task, `accepted` for the ids given and `closed` for the rest; returns the ids of each kind, ascending.
  - `threadOf(db: Db | Tx, taskId: number): ThreadRow[]` every row, by id.
- Produces, `item.ts`:
  - `toItem(row: TaskRow): Item`, `columnsOf(item: Item)` moved unchanged from `lifecycle.ts`, which imports them from `./item` and no longer exports `toItem` (nothing else imports it).
  - `saveItem(tx: Tx, before: TaskRow, item: Item, opts: { set?: { score?: number; agreedAt?: string | null; offerRound?: number }; accepted?: readonly number[] }, now: Date): { row: TaskRow; accepted: number[]; closed: number[] }` is the only code that writes a task's `status`, reservation and completion columns. It saves `columnsOf(item)`, `opts.set` and `updatedAt`. When `before.status` is `proposed` and `item.status` is not, it calls `closeThread(tx, before.id, opts.accepted ?? [], now)` and returns its two lists; otherwise both are `[]`.
  - `runStep` (`lifecycle.ts`) saves through `saveItem(tx, row, next.value, {}, now)` and adds `accepted` and `closed` to its audit entry's `after`.
- Produces, `tasks.ts`:
  - `agreementOf(tx: Db | Tx, task: TaskRow): OneTimeAgreement` (now exported): for a proposed task `offer.proposedBy = openOffer(…).userId` and `book.bids = openBids(…)` as `{ by, score }`.
  - `type AgreedOneTime = Exclude<OneTimeAgreement, { status: 'proposed' }>`
  - `agree(tx: Tx, task: TaskRow, agreed: AgreedOneTime, accepted: readonly number[], actor: Actor, now: Date): TaskRow` replaces `openTask`. It calls `markAgreed(toItem(task), agreed.status === 'reserved' ? { takerId, giverId } : null)` (throws on an error: the caller checked `proposed`), saves it with `saveItem(tx, task, item, { set: { score: agreed.score, agreedAt, offerRound }, accepted }, now)` where `offerRound` is `task.offerRound + 1` when `agreed.score !== task.score`, and writes `task.agreed` with `before: { status, score, offerRound }` and `after: { status, score, offerRound, reservedBy, reservedVia, reservedGiverId, accepted, closed }` (both from `saveItem`).
  - `createTask(db: Db | Tx, …)` (signature widened for the demo seed) adds the first offer with `addEntry`; `approveTaskOffer` and `resolveProposedTasks` end through `agree(tx, task, result, [openOffer(tx, task.id).id], actor, now)`; `reopenOffer` adds the giver's re-offer with `addEntry` and puts its `entryId` into its `task.score_approved` payload.

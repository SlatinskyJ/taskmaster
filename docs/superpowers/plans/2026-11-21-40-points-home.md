# Points query and taker home (Domů) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Issue:** [#40 Points query and taker home (Domů)](https://github.com/SlatinskyJ/taskmaster/issues/40)

**Goal:** a taker opens Domů and sees his points bar (confirmed vs pending vs the two levels) above "Čeká na tebe", his reservations and the open tasks, and can mark an open task Hotovo without reserving it first.

**Architecture:** a read-only points module `src/server/points/` sums task scores per earner and returns them with the current levels; one GET server function serves it (a taker gets only his own row, a giver every taker's row). Domů's loader calls it and renders the existing `PointsBar` (#32). No schema change, no migration, no state change.

**Tech Stack:** TanStack Start server functions, Drizzle/SQLite, React, Vitest.

**Spec:** `docs/superpowers/specs/2026-11-16-taskmaster-design.md` §5.5, §5.7, §7 (home sketch); UI doc `docs/superpowers/specs/2026-11-16-taskmaster-ui-design.md` §3, §4, §6, §7.1.

**Size:** about 170 changed lines outside tests (points module ~60, server function ~20, Domů route ~25, TakerBoard ~40, strings ~5, demo seed ~20).

## Global Constraints

- Czech UI text only in `src/lib/strings.ts`; code in English.
- `src/domain/` stays framework-free.
- Spec §5.7: confirmed = "the running total: carry-over + confirmed this period"; pending = done, unconfirmed, shown separately; both against lower and upper. "Givers see the same for every taker." A taker sees his own.
- Defaults until #42 (periods) lands: lower 50, upper 100 (spec §5.8 defaults; Jakub 2026-11-21: week 1 runs on spec defaults).
- Recurring chores are hidden for launch (Jakub 2026-11-21, separate ad-hoc PR); only one-time tasks earn points here.
- Tap targets ≥ 44 px (`min-h-tap`, `size-tap`); animations have a `motion-reduce:` opt-out.

## Decisions (rulings for the brief)

1. **Running total before periods exist.** No period, settlement or adjustment rows exist yet, so carry-over is 0 and nothing has been deducted: the running total is the sum of `score` over the taker's `confirmed` tasks (`earner_id` = him). Pending is the sum over `done_unconfirmed` tasks with `earner_id` = him. This is exactly what spec §5.7 gives while no settlement has happened. #42 makes `takerPoints` period-aware (levels from the current period; confirmed = carry-over + confirmed in period + adjustments); the screens do not change. Agreed with the #42 thread.
2. **Points bar above "Čeká na tebe".** UI doc §6 [call] says "Čeká na tebe" is always at the top of Domů, and the spec §7 sketch puts the bar in the header, above it. The bar is part of the header (greeting + bar), so "Čeká na tebe" stays the first list. Plan follows the sketch.
3. **Volné rows get Hotovo + Rezervovat.** Spec §5.5 lets a taker mark an open task done without reserving it, and the sketch shows `[Hotovo]` on open rows. On an open row Hotovo keeps its label (main action) and Rezervovat becomes a 44 px icon button (`Bookmark` from lucide-react, `aria-label="Rezervovat"`), the same pattern as Uvolnit on "Moje" rows (#148), so a long name and chip read at 360 px.
4. **No "+ Zapsat udělanou práci" button.** It opens self-logging of a recurring chore (spec §5.3), which is hidden for launch; the button comes back with recurring chores.
5. **Admin** has no Domů (existing guard) and the server function refuses him.

## Review Focus

1. A task a **giver** completed (`earner_id` null, status confirmed) must count for nobody: test in Task 1.
2. A taker with **no tasks at all** must see `0 ✔ + 0 ⏳`, not a missing bar or an error: tests in Task 1 (row with zeros) and Task 3 (bar renders).
3. **Cancelled / open / reserved / proposed** tasks with an `earner_id`-less or reserved state must never add points; a rejected completion goes back to reserved/open and leaves pending: test in Task 1.
4. A taker must **never receive his brother's numbers** from the server function: test in Task 2.
5. Hotovo on an **open** row while another tap is busy must be disabled (shared busy state): test in Task 3.

## UX pre-flight

- Tap targets: Hotovo (`Button` default size is `min-h-tap`), icon Rezervovat (`size="icon"` = `size-tap`). Checked in Task 3 tests by the variant/size props used.
- Motion: `PointsBar` already uses `bar-grow`/`animate-bar-glow`, both behind `useEffectsEnabled` (follows `prefers-reduced-motion`); confetti same. Nothing new animates.
- Busy and failure: Hotovo/Rezervovat use `useTaskAction` (busy key, Czech error toast, the row stays so the user can tap again).
- Loader empty/error: the bar renders zeros for a taker with no points; an empty Volné list keeps its `EmptyState`; a failed loader shows the existing `RouteError` (Zkusit znovu).
- Irreversible actions: none new (Hotovo can be rejected/undone by the giver flow; no dialog, same as on "Moje").
- 360 px: TaskRow wraps the name (existing), the chip and points stay whole; the action area is icon + one labelled button, as on "Moje" rows.

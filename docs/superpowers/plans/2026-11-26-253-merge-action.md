# Merge approved PRs with a GitHub Action: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.

**Issue:** #253 Merge approved PRs with a GitHub Action.
**Goal:** The clean path of a merge-me run (update the PR with `main`, wait for CI, squash-merge, next PR) runs as a GitHub Action with no agent. The agent skill `merge-approved-prs` only runs for PRs the Action hands over.
**Architecture:** A workflow on the default branch runs one Node script per event. The script reads the labelled PRs over the GitHub API, decides with pure functions which single PR to act on, and does one step: record the approved commit, update the branch, merge it, or hand it over with one comment. The Action merges itself with `PUT pulls/<n>/merge` and the `sha` it approved, so GitHub refuses the merge if anything else was pushed. No GitHub auto-merge.
**Tech stack:** GitHub Actions, Node 22 (TS run directly, like `scripts/post-judge-review.ts`), Vitest, `fetch` to the REST and GraphQL APIs (no new npm dependency).
**Spec:** none (tooling). Rules it implements: skill `merge-approved-prs` sections 1 and 2; `CLAUDE.md` labels and Trivial PRs.
**Size:** about 350 changed lines (script about 250, workflow about 60, skill and CLAUDE.md edits about 40), plus tests. Touches CI, a protected area.

## Global constraints

- **Approval = Jakub's label on one commit.** Only a `labeled` event for `merge-me` whose `actor.login` is `SlatinskyJ` counts. The approved commit is `pull_request.head.sha` from that `pull_request_target` `labeled` event's payload, recorded at once by that run as an App marker comment. A PR with a qualifying label but no marker after it (the run was skipped, e.g. before the secrets existed) is handed over with `'approval not recorded: add merge-me again'`; the Action never approves whatever head it finds later. The Action never adds a label; it takes `merge-me` off only after its own merge.
- **What may sit on top of the approved commit:** only merge commits the Action made with update-branch. One is accepted when its parents are exactly `[approved, <a commit on main>]` and `verification.verified` is true with the committer `GitHub <noreply@github.com>` (an API-made commit; a pusher cannot forge that signature). Commit subjects and dates are never trusted.
- **Merge:** `PUT pulls/<n>/merge` with `merge_method: squash` and `sha: <headSha>`, the head that `entryCheck` just found approved (the approved commit, or the Action's update merge on top of it). A push in between makes GitHub refuse (409), and the PR is handed over.
- Never bypass the ruleset, never force-push, never merge while a required check is not passing.
- **Required checks:** names from the main branch ruleset (`GET repos/{o}/{r}/rules/branches/main`, rule `required_status_checks`). An empty name list throws (never "all green"). Per name, the latest check-run on the head SHA from the GitHub Actions app (`app.slug == 'github-actions'`): `success`, `skipped`, `neutral` pass; a name with no run, or a run not completed, is `pending`; anything else is `red`.
- **Hand-over is sticky.** A PR with a hand-over comment from the App after the latest qualifying label is left alone until Jakub labels it again.
- The workflow never checks out or runs PR code: it checks out the default branch only, and runs on `pull_request_target`, `workflow_run`, `push` and `workflow_dispatch`, all of which run default-branch code.
- Every third-party action is pinned to a full commit SHA with a `# vX` comment.
- **Token:** a GitHub App token (`actions/create-github-app-token`, secrets `MERGE_APP_ID`, `MERGE_APP_PRIVATE_KEY`), because work done with `GITHUB_TOKEN` starts no workflows: CI would not run after an update, and `deploy prod` would not run after a merge. The token is narrowed on the step: `repositories: taskmaster`, `permission-contents: write`, `permission-pull-requests: write`, `permission-issues: write`, `permission-checks: read`. If Jakub picks a fine-grained PAT instead, only the token step changes (secret `MERGE_TOKEN`, same permissions).
- English code, logs and comments. Every comment from the Action ends with `---\n_Posted by the merge-me Action_`.

## Review focus

1. A commit pushed after the label, in any form (new subject, fake merge commit, back-dated, force-push): handed over, never merged. Tests in Task 1 and Task 2.
2. `main` moves while a PR's CI runs: the PR is behind again, so the next run updates it again, and only that PR. Test in Task 1.
3. An update with a conflict (HTTP 422) or a merge refused (405/409): hand over once, move on. Tests in Task 2.
4. The same event firing twice: no second comment, no second update while CI is pending. Tests in Task 1 and Task 2.
5. A PR in a GitHub stack, or labelled by someone other than Jakub: handed over or ignored, never merged. Tests in Task 1 and Task 2.

    headSha: string

    | { kind: 'wait'; pr: number }

  function nextActions(prs: PrFacts[]): Action[]

### Task 2: GitHub facts, the run, and their tests

**Files:**
- Create: `scripts/merge-queue/github.ts` (REST and GraphQL over `fetch`, token from `GH_TOKEN`; `fetch` injectable)
- Create: `scripts/merge-queue/run.ts` (entry: `node scripts/merge-queue/run.ts`)
- Test: `tests/merge-queue-github.test.ts`, `tests/merge-queue-run.test.ts`

**Interfaces:**
- Consumes: Task 1.
- Produces:
  ```ts
  const APPROVED_MARKER = '<!-- merge-queue:approved '   // + sha + ' -->'
  const HANDOFF_MARKER = '<!-- merge-queue:handoff -->'
  interface Gh {
    labelledPrs(): Promise<PrFacts[]>
    updateBranch(pr: number, expectedHead: string): Promise<'ok' | 'conflict'>  // 422 → 'conflict'
    merge(pr: number, sha: string): Promise<'merged' | 'refused'>              // 405/409 → 'refused'
    comment(pr: number, body: string): Promise<void>
    removeLabel(pr: number, label: string): Promise<void>
  }
  function makeGh(token: string, botLogin: string, fetchImpl?: typeof fetch): Gh   // botLogin = `${app-slug}[bot]`
  function acceptedUpdate(commit: GhCommit, approvedSha: string, mainShas: Set<string>): boolean
  function requiredCi(names: string[], runs: GhCheckRun[]): Ci
  function run(gh: Gh, log: (line: string) => void, labelEvent?: { pr: number; sha: string }): Promise<void>
  // labelEvent: from the workflow's pull_request_target payload (env LABEL_PR, LABEL_SHA, set only for a
  // labeled event whose sender is SlatinskyJ). run() first writes the approval marker for it, then decides.
  ```
- Facts sources: qualifying label = last `labeled` event for `merge-me` with `actor.login === 'SlatinskyJ'` (`issues/<n>/events`; no such event = PR ignored); markers = `issues/<n>/comments` whose `user.login` is `botLogin` (env `BOT_LOGIN`, from the token step's `app-slug` output plus `[bot]`; `GET /app` needs a JWT the script does not have) created after that event; `headIsApproved` walks `pulls/<n>/commits` from the approved SHA to head, every commit after it passing `acceptedUpdate`; `mainShas` holds each candidate second parent for which `compare/<parent>...main` reports `status: 'behind'` or `'identical'` (it is on main); threads from GraphQL `reviewThreads(first:100){nodes{isResolved}}`; stack from `stacks?pull_request=<n>`; `behind` from `pulls/<n>` `mergeable_state === 'behind'`.
- `updatedByAction`: the head is not the approved SHA and is an accepted update.

# Weekly meeting, part 1 of 2: settlement records and meeting server functions — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Issue:** [#44 Weekly meeting: clear pending, settle, plan](https://github.com/SlatinskyJ/taskmaster/issues/44), part (a) of the 2-PR stack the issue proposes. Part (b), the M1/M2/M3 screens, goes on top.

**Goal:** a giver can read the meeting's state (which week to settle, what is still pending before its end, each taker's total, level, deduction and carry-over) and confirm the settlement, which writes final settlement records with audit entries and, for the running week, ends it.

**Architecture:** the arithmetic exists in `src/domain/settlement.ts` (`settle`, `runningTotal`). This PR adds one domain rule (which period the meeting settles), a `settlements` table that cannot be updated or deleted, and `src/server/settlement/` with a ledger reader, `getMeeting` and `settlePeriod`, plus two giver-only server functions. Stacked on [#164 Periods](https://github.com/SlatinskyJ/taskmaster/pull/164) (`endRunningPeriod`, `listPeriods`).

**Tech Stack:** TypeScript strict, Drizzle + better-sqlite3, TanStack Start server functions, Vitest.

**Spec:** `docs/superpowers/specs/2026-11-16-taskmaster-design.md` §5.9 (meeting steps 1 and 2, settlement records, final), §5.8 (settling ends the period; settling a period ended at its cutoff), §5.5 (attribution by `completed_at`), §5.10 (audit), §5.11 (disputes never block — nothing to do here).

**Size:** about 380 changed lines without tests and the migration (domain ~40, schema ~50, ledger ~50, meeting/settle ~170, server functions ~60, points wiring ~10). One PR: the table without `settlePeriod` has no writer, and `settlePeriod` is what the screens need.

**Judges:** Rules, Security, Architecture, Tests.

## Global Constraints

- §5.9 arithmetic, unchanged, through domain `settle`: total ≥ upper → upper, deduct upper; lower ≤ total < upper → lower, deduct lower; total < lower → none, deduct 0. Carry-over = total − deducted. Never negative.
- Total for a taker at a settlement = **running total up to the period's end** = confirmed points of tasks they earned with `completed_at` before the end − every earlier settlement's deduction (± adjustments, which don't exist yet: #48).
- The period's end for the meeting: now if the period is running, else its stored end (§5.9 step 1: "the cutoff, or now if the meeting runs before the cutoff").
- Step 2 is refused while any task is `done_unconfirmed` with `completed_at` before that end. Later ones stay pending and don't block.
- Settlements are final: no update or delete path in code, and DB triggers reject `UPDATE`/`DELETE` on `settlements`.
- One transaction: all records, their `settlement.created` audit entries, and (running period) `endRunningPeriod`. Any failure rolls back everything.
- Only an active giver settles. Admin never (§3). Disputes don't block (§5.11 [call]).
- Czech text: none in this PR (screens are part b). Codes and errors in English.
- Never put a production host name anywhere.

## Rulings (spec silent; recorded in the PR brief)

1. **Which week the meeting settles** (§5.8: a week that ended at its cutoff "can be settled any time after"): the **oldest ended week that has no settlement** (the meeting was missed or runs late, e.g. Monday). Only when every ended week is settled does the meeting settle the running week (which ends it). Weeks are never skipped: if two Sundays were missed, the giver settles the older one, then the meeting offers the next. "Ended" = `periodEnd(p) <= now`, so the moment between a cutoff and its roll tick still finds the ended week. Nothing to settle → the meeting shows nothing to do. The brief puts this in front of Jakub as a reading he may overturn.
2. **Takers settled** = every active taker, also one with 0 points (a record with level none, 0 deducted, 0 carried), so history shows every taker every week.
3. **The giver confirms the week he saw:** `settlePeriod` takes the period id from the screen and refuses `wrong_period` if the target has changed meanwhile (e.g. the cutoff roll ran between opening and confirming).
4. **The giver confirms the totals he saw.** The confirm sends the totals shown per taker (`shown: { takerId, total }[]`). The server recomputes them in the transaction and refuses `totals_changed` (nothing written) if the set of takers or any total differs, e.g. a no-approval task completed while the screen was open. The screen (part b) then reloads and shows the fresh preview.

## Review Focus

1. **Meeting held Monday after a missed Sunday.** The ended week is settled, not the running one; the running week is not ended; completions done Monday morning count for the next settlement, not this one. → Task 1 test `missed Sunday: settles the ended week`; Task 3 test `late meeting: total excludes completions after the cutoff`.
2. **A completion approved during the meeting after its total was shown, or two givers confirming at once.** A changed total → `totals_changed`, nothing written; the second of two confirms finds the period settled → `already_settled`, nothing written twice. → Task 3 tests `totals changed since the screen`, `second settle is already_settled`, `the unique index rejects a duplicate record`.
3. **Pending item done exactly at the end instant / 1 ms before.** 1 ms before blocks; at the end it does not. → Task 3 test `pending boundary at the period end`.
4. **Total exactly at a level (50, 100), and 0.** Upper at 100 deducts 100 and carries 0; 49 is none; 0 writes a zero record. → Task 3 test `level boundaries end to end` with the spec examples (130 → upper, 100 deducted, 30 carried; 30 → none).
5. **Audit write fails half way (second taker's entry).** Nothing stays: no records, no early end. → Task 3 test `a failed audit write rolls back every record and the early end`.

# Dispute a locked item: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Issue:** [#46 Dispute a locked item](https://github.com/SlatinskyJ/taskmaster/issues/46) (epic #11).

**Goal:** a taker or a giver flags a locked item as disputed with a reason, sees "Sporné" on it while it is open, and sees the admin's outcome once it is closed; all behind a new launch switch `disputes`.

**Architecture:** one new table `disputes` (one row per dispute, open → dismissed/corrected) and a server module `src/server/disputes/` that loads the disputed record, runs the existing domain rule `openDispute` (`src/domain/disputes.ts`) and writes the row and its audit entry in one transaction. Screens read a small `DisputeMark` per item (open, or the latest outcome with the admin's note) and show a `DisputeControl` (Rozporovat button / Sporné chip / outcome line) next to each locked item. The switch hides every entry point and makes every server function answer `feature_off`.

**Tech Stack:** TanStack Start server functions, Drizzle + better-sqlite3, React, shadcn Drawer, Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-16-taskmaster-design.md` §5.11 (disputes), §5.10 (audit), §3 (who may dispute); UI doc `docs/superpowers/specs/2026-11-16-taskmaster-ui-design.md` §2.2 (Sporné colours), §5 (Drawer), §7.1 TWeek/TDispute, §8 (Rozporovat for givers too).

## Decisions this plan makes (go in the PR brief)

1. **Which records, keyed how.** `item_kind` + `item_id`:
   - `task_score` → `tasks.id`, locked when `tasks.agreed_at IS NOT NULL` (one-time task or instance; a cancelled task that was agreed stays locked).
   - `template_score` → `templates.id`, locked when `templates.status = 'active'`.
   - `completion` → `tasks.id`, locked when `tasks.status = 'confirmed'` (a task is confirmed once, for good).
   - `rejection` → the `audit_log.id` of the `task.rejected` entry. A rejected completion has no row of its own (`src/server/tasks/rejections.ts`); a task can be rejected several times, so the task id would not name one rejection.
   - `settlement` → `settlements.id`.
   - `adjustment` → reserved in the CHECK list for PR 3 (no table yet). This PR's loader answers `not_found` for it.
2. **Domain:** add kind `rejection` to `DisputeKind`/`DisputeTarget` (always locked), because a rejected completion's id space is not the completion's. `completion` keeps its `outcome` field but is locked only when `confirmed` (a rejected one is named by kind `rejection`, so it has exactly one way to be named and the one-open-per-item check holds).
3. **Where Rozporovat shows** (UI doc §7.1 TWeek, §8):
   - Týden → Tento týden: on each confirmed and each rejected item (this period's items, the only completions a screen lists).
   - Týden → Historie: on each settlement record.
   - Task page `/ukol/$taskId`: on the score, once agreed; and on the completion, once confirmed (this reaches older confirmed completions: givers open any task from Úkoly, everyone from links that already lead there).
   - Template page `/sablona/$templateId`: on the score, once active.
   Givers see the same buttons on the same items. A taker's confirmed completion from an earlier week, and any rejection from an earlier week, has no screen of his today: asked Jakub in the thread (recommended: this week's items + the task page + the week's settlement record are enough; else a follow-up adds an entry point). This PR builds the recommended option.
4. **Sporné does not replace the item's state chip** (spec: "keeps its values and state"): the item keeps its chip and points; a second chip "Sporné" (state colour `disputed`) appears in the DisputeControl line under it.
5. **Outcome display** ("everyone involved sees the outcome"): two places. (a) On the item, wherever it shows: the latest closed dispute's outcome and the admin's note, until a new dispute is opened. (b) A lasting list **Rozporováno** at the top of Týden → Historie: the viewer's disputes, newest first, at most 20, each with what it is about, who opened it, the reason, and Sporné or the outcome with the note. It outlives the week, so a dispute closed after the meeting is still seen. "Involved" = a giver sees every dispute; a taker sees the ones he opened, the ones on his own completions, rejections and settlements, and every score dispute (scores are shared by all parties). Nobody gets a notification (no push in v1).
6. **Reason length:** 1–200 characters after trimming (same as a rejection reason, `REASON_MAX`), stored trimmed.
7. **No withdraw.** Spec has none; a dispute closes only by the admin.
8. **Audit `after`** of `dispute.opened` = `{ itemKind, itemId, reason, value }`; `value` is the item's numbers when disputed (`{ score }` for scores, completions and rejections; `{ level, deducted }` for a settlement), so the log says what was disputed even after a later score change. An open dispute does not block a score change (spec: "blocks nothing"; "keeps its values" = the dispute itself changes nothing).
9. **Resolved rows are final:** DB triggers refuse DELETE always, and UPDATE of a row whose old status is not `open` (same idea as `0015_settlements_final`).

## Review Focus

1. Two taps on Poslat správci (or two people at once) on the same item → exactly one open dispute; the second gets "Už je rozporováno." (partial unique index + mapped constraint error, Task 3).
2. Switch off → no Rozporovat anywhere and `openDisputeFn` writes nothing (Task 4, Task 6).
3. A taker opens a dispute on an item that is not locked any more / never was (a proposed task, a pending completion, an id that does not exist) → refused, nothing written (Task 3).
4. A long Czech task name plus a long admin note at 360 px: the note wraps, the button stays whole (Task 6, screenshots).
5. A failure while sending keeps the drawer open with the typed reason and a Czech message, so the boy can tap again (Task 5).

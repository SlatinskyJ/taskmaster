# Live change banner, PR 2: screens subscribe Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task (CLAUDE.md PR flow step 3). Steps use checkbox (`- [ ]`) syntax for tracking.

**Issue:** [#299 Live change banner](https://github.com/SlatinskyJ/taskmaster/issues/299), PR 2 of a stack on [#301 Live change banner](https://github.com/SlatinskyJ/taskmaster/pull/301) (branch `299-live-hub`).

**Goal:** Every screen's data functions return, next to their data, a signed subscription for the topics they read, per viewer; the token carries the viewer's role and a token whose role is not the session user's is refused at stream open.

**Architecture:** Each read server function gets a `liveRead` definition (`read` + `topics`) in its own module; its handler calls `serveLive`, which reads and then signs the topics in the same synchronous block, and returns `{ data, live }`. Loaders unwrap the data with a small collector and return the subscriptions as `live: LiveSub[]` (the client in PR 4 opens the stream from them). No client, no visible change in this PR.

**Tech Stack:** TanStack Start server functions, better-sqlite3 / Drizzle, Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-26-live-changes-design.md` (on `299-live-hub`), sections "The query (subscription)", "Topics", "Connection and limits" (topic limit), "Drift" (per-screen test). Server side so far: `src/server/live/README.md`.

**Size:** about 380 changed lines without tests: role in token ~25, `templates:new` ~10, `read.ts` + collector ~60, read definitions in 9 modules ~190, loaders in 11 routes ~70, README ~25.

**Judges (plan phase):** Rules, Architecture, Tests, Security (the token's role check is a role check, pr-review-rounds §2 exception). Code phase adds nothing visible: no UX, no `preview` label.

## Global Constraints

- Topics are per viewer: a screen subscribes only to topics its reads checked the viewer may load (design "Topics are per viewer"). A per-taker fact goes only on `points:<taker>` (`src/server/live/topics.ts`).
- `liveSubscription` is called after the reads **in the same synchronous block** (README "Subscribing"): every `read` is synchronous; nothing awaits between it and the signing.
- `TOPIC_LIMIT` = 20 (twice the largest screen, design "Limits"); every screen's union of topics on the demo data stays at or under it.
- No separate authorization layer for topics (Jakub 2026-11-26): tokens are signed, so a client can't forge topics; each data function's topics follow its own visibility checks, and review catches topic mistakes.
- Out of scope topics: launch switches, passkeys, logins. Profil (`listMyPasskeysFn`, `getPasskeysEnabledFn`), Správa's `listPasskeyCountsFn`, Klíč and Nový issue no topics: a screen with no topics opens no stream.
- Never `before` / `after` to a client; this PR adds nothing to the wire except the token's role.
- Code, identifiers, logs in English; no Czech text in this PR.

## Review Focus

1. **A boy subscribes to something only a parent may load.** Taker on Týden with a brother's settlement, adjustment or dispute on them: the screen's topics must not catch it (Task 8 must-not-catch cases).
2. **A loader calls a data function the drift test does not know.** A new `…Fn` in a loader with no registry row must fail CI (Task 8 source scan).
3. **A boy with many proposed chores waiting** on Domů: one `template:<id>` per row; past 15 the screen's union exceeds 20 and the stream answers 400. The screen must still load (signing never throws on a long list in production; Task 3), and the limit test pins the demo count. See "Needs Jakub" below.
4. **A token issued under one role used after a role change** (a parent made a boy, or the reverse): refused at open (401), and an open stream ends at the next ping (PR 1 test kept).
5. **A switch-off read** (`{ error: 'feature_off' }`, a null task or template): issues no topics and no token, never a token for an id the viewer could not load (Tasks 4 to 7).

### Task 3: `liveRead`, `serveLive` and the loader collector

**Files:**
- Create: `src/server/live/read.ts`, `src/lib/liveSubs.ts`
- Modify: `src/server/live/index.ts`, `src/server/live/functions.ts` (type re-exports for screens), `src/server/live/subscription.ts`
- Test: `src/server/live/read.test.ts`, `src/lib/liveSubs.test.ts`

**Interfaces:**
- Produces (server):
  ```ts
  export interface Live<T> { data: T; live: LiveSub | null }
  export interface LiveRead<A, T> {
    read: (db: Db, viewer: CurrentUser, arg: A, now: Date) => NotAsync<T>
    topics: (viewer: CurrentUser, data: T, db: Db) => readonly Topic[]
  }
  export function liveRead<A, T>(def: LiveRead<A, T>): LiveRead<A, T>   // identity, for inference
  export function serveLive<A, T>(def: LiveRead<A, T>, viewer: CurrentUser, arg: A, now?: Date): Live<T>
  export function serveLiveIn<A, T>(db: Db, key: string | undefined, def: LiveRead<A, T>, viewer: CurrentUser, arg: A, now: Date): Live<T>
  ```
  `serveLive` = `serveLiveIn(getDb(), sessionToken(), …, now ?? new Date())`. `serveLiveIn`: `read`, then `topics`, deduplicated and sorted, then `liveSubscriptionIn`; no topics → `live: null`.
- `liveSubscriptionIn` on a list over `TOPIC_LIMIT`: throws when `process.env.NODE_ENV !== 'production'`, else `console.error('[live] …')` and returns null, so the screen loads without a banner (Review Focus 3). An invalid topic string still throws everywhere (a programming error).
- Produces (client, `src/lib/liveSubs.ts`): `liveSubs(): { take<T>(r: Live<T>): T; all(): LiveSub[] }` (`all()` drops nulls). Types imported with `import type` from `~/server/live/functions`, which re-exports `Live` and `LiveSub`.

## #304 (two saves in one microtask share a change)

Left to PR 3, not this PR. Reason: it changes how changes are keyed (audit `currentChange`) and which tab a change came from (hub `pending.origin`), both on the event path PR 3 reworks for the text; nothing in PR 2 sends an event to a person, and the banner turns on only in PR 4. ## Needs Jakub (spec gap)

The design says the topic limit fails CI "rather than being refused in use". One screen's count grows with the data: a boy's Domů takes a `template:<id>` per proposed chore waiting for him (he may not hold `templates:proposed`). Past 15 waiting chores the stream refuses it and his Domů gets no banner. Options: (a) accept it (a family rarely has that many proposed chores at once; logged on the server); (b) a broader topic for the boys' waiting chores, which tells a boy when a proposed chore he no longer sees changes (no text, but an event). This plan builds (a).

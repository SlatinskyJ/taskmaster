# Live change banner: banner and refresh. Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task (CLAUDE.md PR flow step 3). Steps use checkbox (`- [ ]`) syntax for tracking.

**Issue:** Part of [#299 Live change banner](https://github.com/SlatinskyJ/taskmaster/issues/299), PR 4 of 4 (stacked on PR 3 [#312 Live change banner: event texts](https://github.com/SlatinskyJ/taskmaster/pull/312), branch `299-live-texts`).

**Goal:** When another person's change touches data the open screen loaded, a sticky Sonner banner shows that change's sentence (or "Více změn (N)") with a refresh button that reloads the screen in place; one's own changes in the same tab show nothing.

**Architecture:** One `<LiveBanner />` in the `_app` layout collects the `live: LiveSub[]` that every active route's loader already returns (PR 2), opens one `fetch`-based SSE stream per tab with those tokens, counts changes in a pure reducer and renders one Sonner toast with a fixed id. Refresh is `router.invalidate()`: every active loader runs again and returns new tokens, so the layout closes the old stream, opens a new one and clears the banner. Screens add no code.

**Tech Stack:** React 19, TanStack Router/Start, Sonner 2.0.8 (already a dependency), lucide-react, Vitest, Playwright. No new dependency.

**Spec:** `docs/superpowers/specs/2026-11-26-live-changes-design.md` (sections Goals, "Leaving a screen ends its subscription", Own-tab changes, The banner, Connection and limits, Drift's e2e line); `docs/superpowers/specs/2026-11-16-taskmaster-design.md` §2 (banner exception) and §5.12 ("the giver's screen shows the live change banner and updates when the giver taps it"). Server side as built: `src/server/live/README.md`.

**Size:** about 440 changed lines outside tests (client stream ~130, banner state with dismiss guard ~80, banner component ~110, server `replaced` signal ~20, dialog/drawer guard ~15, strings ~10, README ~40, layout and CSS ~10). One PR: the stream client has nothing to show without the banner, and the banner has nothing to count without the stream; neither part can be judged alone.

## Global Constraints

- Czech UI text only in `src/lib/strings.ts`; code, identifiers, logs in English.
- Banner: "one Sonner toast with a fixed id, updated in place: no timeout, swipe up or close to dismiss, refresh icon button (`aria-label` "Načíst změny" **[call]**)".
- One change: its sentence (`LiveEvent.text`, e.g. `Táta · domluveno za 8 b · Vynést koš`). Another while it shows: `Více změn (2)`, counting up.
- "The count runs from the last refresh": dismiss without refresh, and the next change shows `Více změn (3)`.
- "The count lives in the tab and resets on refresh and on navigation." Refresh reloads the data "as after one's own action", so the reload after one's own action renews the subscription and clears the banner the same way.
- Refresh = `router.invalidate()`, never a browser reload. Typed inputs stay.
- Own change in this tab: no notice (the hub already skips the tab, `x-tm-tab`). Same person on another tab/phone: notice (`Ty · …`).
- "On navigation the tab closes the old stream and opens one with the new screen's topics and `asOf`"; "an event from a closed one that was already in flight is dropped by the tab". One open stream per tab.
- Switch `liveChanges` off: no stream is opened, nothing changes.
- The banner must not steal focus or make the screen jump (anti-goals). It shows at once, also over a focused field in a dialog or sheet; the typed input survives Zavřít and Načíst změny (Jakub 2026-11-27, Q2).
- Every tap target ≥ 44 px (`size-tap`); every animation has a `motion-reduce:` opt-out.
- Wire format (README "The stream"): `GET /api/live?t=…&t=…&since=<id>&tab=<tabId>`; body `: open`, then `id: <n>\ndata: <LiveEvent JSON>\n\n`, `event: overflow` (id = newest), `: ping` every 25 s. 401 / 404 / 400 / 503 as listed there. A viewer frame sends its `x-tm-frame` header (`frameHeader(window)`).

## How a screen hooks into the refresh (for #313 and later screens)

- A screen is live when its route loader returns `live: live.all()` (PR 2's `liveSubs()`); nothing else. `<LiveBanner />` in `src/routes/_app.tsx` reads every active match's `loaderData.live`.
- The banner's refresh calls `router.invalidate()`. That reruns every active loader, which signs new tokens with a new `asOf`; the layout sees a new subscription key, closes the old stream, opens the new one and clears the banner and its count. So a refresh always renews the subscription (answers the Architecture nit on PR #307 in #313). The client modules sit next to PR 2's `src/lib/liveSubs.ts` (`liveSse.ts`, `liveConnect.ts`, `liveBanner.ts`), so the live client code is in one place.
- A screen that must know whether the banner is its refresh (e.g. #313 hiding Schůzka's Obnovit) calls `offersLiveRefresh(features, live)` from `~/lib/liveBanner` with `context.features` and its loader's `live`: true when the switch is on and the loader returned at least one subscription. Schůzka's own Obnovit (`planRefresh.ts`) calls `getWeekPlanFn` directly and does not renew the subscription; #313 removes it when `offersLiveRefresh` is true. This PR does not touch Schůzka.

## Review Focus

1. **A redeploy or a lost connection silences the tab.** Every merge restarts production; the proxy answers 502/503 meanwhile, and a phone wakes from sleep with a dead socket. Expected: the tab reconnects with `since=<last id>` and the banner then counts the missed changes. Native `EventSource` gives up for good after a non-200, so the client is `fetch`-based with its own retry (Task 2 tests 502, network error, and a silent socket past 60 s).
2. **A fourth tab of one login.** The server closes the oldest stream; an auto-reconnect would evict the next one, round and round, until the tab in hand loses its stream too. Expected: the tab in hand keeps working; an evicted tab reopens only when it is visible and focused again (Task 1 adds the `replaced` signal, Task 2 tests it).
3. **Tapping the banner while a dialog or sheet is open.** Radix closes a modal on an outside pointer-down and blocks pointer events outside it, so tapping refresh would close "Zrušit úkol?" and throw away the typed reason. Expected: refresh works and the dialog stays open with its text (Task 5 guard; the two-browser e2e taps refresh with the dialog open).
4. **An event in flight from the previous screen.** Navigation closes the old stream; a frame already read must not count on the new screen. Expected: dropped (Task 2 test "drops a frame read after close"; Task 4 test on key change).
5. **The keyboard is open and the banner arrives.** Expected (Jakub 2026-11-27): the banner shows at once; the field keeps focus and its text; Zavřít and Načíst změny leave the dialog or sheet open with what was typed (Task 6 keyboard case).

- Produces (`liveConnect.ts`):
  ```ts
  export interface LiveHandlers { change(e: LiveEvent): void; overflow(): void }
  export interface ConnectDeps {
    fetch: typeof fetch
    setTimeout: (run: () => void, ms: number) => unknown
    clearTimeout: (h: unknown) => void
    isVisible: () => boolean
    /** Calls back when the tab is visible and focused again, or back online; returns unsubscribe. */
    onInHand: (run: () => void) => () => void
    headers: Record<string, string>   // frameHeader(window)
  }
  export const RETRY_MS: readonly number[]  // [1_000, 2_000, 5_000, 10_000, 30_000, 60_000], then 60_000
  export const STALE_MS = 60_000            // no byte (data or ping) for this long: reconnect
  export function liveUrl(subs: readonly LiveSub[], tab: string, since: number | null): string
  export function connectLive(subs: readonly LiveSub[], tab: string, on: LiveHandlers, deps: ConnectDeps): { close(): void }
  ```
- Rules the tests pin: first request has no `since`; a reconnect sends `since=<id of the last frame with an id>` (events and overflow); `: open` resets the retry index; status 401, 404 and 400 stop for good (400 logs `[live] stream refused: 400`, no tokens); 503, any other status, a network error and a clean end retry after `RETRY_MS[i]`; `replaced` stops and reopens only on `onInHand`; while hidden no retry fires, `onInHand` retries at once; after `close()` no handler runs and no timer is left (a frame already read is dropped). A `data` that is not a `LiveEvent` (`id`, `change` numbers, `text` string) is ignored.

### Task 3: Banner state and text

**Files:**

**Interfaces:**
- Strings: `cs.live.banner = { many: (n: number) => \`Více změn (${String(n)})\`, overflow: <Q1>, refresh: 'Načíst změny', close: 'Zavřít' }`.
- Produces:
  ```ts
  export interface BannerState { changes: ReadonlySet<number>; text: string | null; overflow: boolean; shown: boolean }
  export const BANNER_START: BannerState
  export type BannerEvent =
    | { type: 'change'; event: Pick<LiveEvent, 'change' | 'text'> }
    | { type: 'overflow' }
    | { type: 'dismiss' }
  /** Ties one shown toast's dismiss to the key it was shown for (Sonner 2.0.8 also calls `onDismiss` from an effect after a programmatic `toast.dismiss`). */
  export function dismissGuard(key: string, currentKey: () => string, dismiss: () => void): {
    onDismiss(): void   // Sonner's callback (swipe, and every later effect)
    close(): void       // the X button: dispatches once, then toast.dismiss
    drop(): void        // a programmatic dismiss (key change): never dispatches
  }
  export function bannerReduce(s: BannerState, e: BannerEvent): BannerState
  /** What the toast says, or null for no toast. */
  export function bannerText(s: BannerState): string | null
  /** The live subscriptions of the active matches, in match order, deduplicated by token. */
  export function subsOf(matches: readonly { loaderData?: unknown }[]): LiveSub[]
  /** Identity of a screen's subscription: the tokens joined. Empty string for none. */
  export function subsKey(subs: readonly LiveSub[]): string
  /** #313: the banner is this screen's refresh. */
  export function offersLiveRefresh(features: Pick<Features, 'liveChanges'>, live: readonly LiveSub[]): boolean
  ```
- Rules: a change key already counted changes nothing, neither the count nor `shown` (a replay overlap after a dismiss must not bring the banner back with the same number); a new change sets `shown: true`; `dismiss` keeps the count; one change → its `text`; two or more → `many(n)`; overflow → `overflow` text, also with later changes (Q1). There is no `reset` event: a new subscription key starts from `BANNER_START` (Task 4).

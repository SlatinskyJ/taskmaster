# Scheduler Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Issue:** [#39 Scheduler: scheduled instances, expiry, catch-up on boot](https://github.com/SlatinskyJ/taskmaster/issues/39)

**Goal:** In-process jobs that make scheduled instances of agreed templates, expire deadline instances after their grace window, and roll periods, all idempotent and caught up on boot after downtime.

**Architecture:** One scheduler (`src/server/scheduler/`) runs a list of jobs once at boot and then every minute on a `croner` tick in Europe/Prague. Each job is a plain function `(at: Date) => void` over the DB that does what is due at `at` and nothing when nothing is due, so running it twice, late, or after a restart is safe. Three jobs: periods (the existing `rollPeriods`, taking over the period roller's loop), expiry (`expireItem` from the domain, which already exists), scheduled instances (new domain slot maths plus a small table that remembers each template's last handled slot). The roller's own loop (`src/server/periods/roller.ts`) is deleted.

**Tech Stack:** TanStack Start (Nitro plugin), Drizzle + SQLite, `croner` 10.0.1 (new dependency, spec §11), Vitest with fake timers.

**Spec:** `docs/superpowers/specs/2026-11-16-taskmaster-design.md` §5.3 (origin 1, deadline + grace, the no-duplicate [call]), §5.6 (expired), §5.8 (period roll), §5.10 (audit), §11 (Scheduler [call]).

**Stack:** on [#187 Instances on demand and self-logged chores](https://github.com/SlatinskyJ/taskmaster/pull/187) (instance rows, `instanceDeadline`, `origin 'scheduled'`, the Prošlo group). Base branch `38-instances-and-log`; added to #187's GitHub stack when the PR opens.

**Size:** about 330 changed lines without tests, the migration and generated files: domain 45, schema 15, scheduled instances 100, expiry 45, scheduler 60, plugin 15, rows and strings 20, demo 10, `package.json` 1. Under the 400 mark.

## Global Constraints

- Prague wall-clock maths only through `src/domain/dates.ts` (DST rules there: a wall time in the spring gap moves forward, a doubled one resolves to the second occurrence); store UTC with `toIsoUtc`.
- `src/domain/` stays framework-free.
- Every state change writes its audit entry in the same transaction (`writeAudit`), actor `{ kind: 'system' }`, entity type `task` for instance rows (rule from #38, in `src/server/audit/README.md`).
- Never edit a committed migration: add one with `pnpm db:generate --name scheduler`. Track B's open PRs #186 (`0018_period_settings`) and #191 (`0019_period_proposals`) and #187 (`0018_instances`) take the same numbers; whichever lands later regenerates its unmerged migration with the next free number (never edits a merged one). This plan calls it `0019_scheduler` for short.
- A job never throws out of the scheduler: a failure is logged with the job name and the next tick tries again.
- Czech UI text only in `src/lib/strings.ts`.
- Production switches stay off; nothing here turns `recurring` on (`src/server/features/README.md`). The scheduler runs regardless of the switch: with the switch off no template can be agreed in the UI, so there is nothing to schedule.

## Rulings (all go into the PR brief)

1. **One tick per minute** (`'* * * * *'`, zone Europe/Prague, `protect: true` so ticks never overlap, `unref: true` so the timer doesn't hold the process). Every job checks the DB on each tick instead of each one computing its own next wake time. Why: schedules, deadlines and the period end live in the DB and change when people act ("+ Teď", a template agreed, a meeting settles); a fixed tick needs no wake-up calls from those actions. Cost: a slot or an expiry happens up to a minute late; the domain already refuses a completion after grace (`past_grace`), so a late status flip changes no points. A tick is a handful of indexed queries.
2. **Boot catch-up = the first tick, run at once** when the scheduler starts (before croner's first minute), in job order periods → expiry → instances. Periods first, so an instance made by the catch-up falls after any roll; expiry before instances, so the no-duplicate check (ruling 5) does not count an instance that is about to expire.
3. **A slot** is a moment a template's schedule says an instance appears: one of `schedule.days` at `schedule.time`, or at the start of the Prague day when `time` is null (the #37 [call]). Only slots at or after the template's `agreedAt` count: a template agreed Tuesday 19:00 with "Tuesday 18:00" first appears next Tuesday.
4. **Missed slots after downtime: only the latest one per template** (asked Jakub on a decision card in the project thread, recommended this). The instances job takes the latest slot at or before `at`; if it is newer than the template's last handled slot it is handled, and any older missed slots are skipped. A deadline slot whose grace window has already ended at `at` is handled without making an instance (it could only be born expired). If Jakub picks "every missed one", Task 3 instead walks every slot after the last handled one, oldest first, and makes each (one past grace is made and expired in the same transaction, both logged); the plan is updated before the build.
5. **No-duplicate [call] (spec §5.3):** for a template without a deadline, the slot makes no instance while an earlier instance of the same template, of any origin, is still `open` or `reserved`. The slot still counts as handled, so finishing the old instance later does not make the skipped one appear late.
6. **Last handled slot** is stored in a new table `template_slots (template_id PK → templates.id, last_slot_at TEXT NOT NULL)`, written in the same transaction as the instance (or as the decision to skip). It is scheduler bookkeeping, not a family-visible state change, so it writes no audit entry; what the family sees (an instance born, or none) is logged through `instance.created`. Never deleted, like the rest.
7. **A scheduled instance** is born like "+ Teď" (#38): `tasks` row with `origin 'scheduled'`, title, score and approval flag copied from the template at that moment, due time `instanceDeadline(rule, slot)` (from the slot, not from the tick, so a tick a minute late does not shift the due time), `created_by` = the template's creator (the column is NOT NULL; the audit actor says it was the system), `created_at` = the tick. Audit `instance.created`, actor system, `after` as for on-demand plus `slotAt`.
8. **Expiry:** every `open` or `reserved` row with `grace_ends_at <= at` goes through `expireItem` (domain) to `expired`; a reservation is dropped with it. Audit `instance.expired`, actor system, entity `task`, `before`/`after` like the task steps. One transaction per row, so one bad row does not block the rest.
9. **The period roller's loop goes away;** its job is `rollPeriods(db, at, defaults())` each tick, where `defaults` is passed in by the boot plugin: `() => DEFAULT_PERIOD_DEFAULTS` on this branch today; once Track B's [#186](https://github.com/SlatinskyJ/taskmaster/pull/186) is in the base, `() => getPeriodDefaults(db)` read per tick (an admin's save applies at the next roll), and the job keeps #186's log line with each started period's levels. #191's `rollPeriods` also applies agreed proposals; the job only calls `rollPeriods` (agreed with that thread). `startPeriodRoller`, `roller.ts` and `roller.test.ts` are deleted; their behaviours (catch up at boot, roll at cutoff, log new periods, survive a failure) move to the scheduler and job tests.
10. **Row text for a scheduled instance without a deadline:** "naplánováno · út 18:00" (`cs.instances.scheduledAt(weekday, time)`), from `createdAt`, like "na vyžádání · 15:20". With a deadline the due text wins, as for on-demand. History line for `instance.expired`: "prošlo" (`cs.history.expired`), for a scheduled `instance.created` (actor system): "přidáno podle rozvrhu za {n} b" (`cs.history.scheduledCreated`).

## Review Focus

1. A schedule time inside the spring DST gap (02:30 on 29 March 2026) or the doubled hour (02:30 on 25 October 2026): one slot that day, at the instant `fromPragueWallTime` gives, never two and never none (Task 1).
2. A restart in the same minute as a slot, or two ticks for the same slot, makes exactly one instance (Task 3: run the job twice at the slot instant and a minute later, expect one row).
3. A tick exactly at `grace_ends_at` expires the row (half-open, as `pastGrace`), a tick one millisecond before does not (Task 4).
4. A failing job (throws) does not stop the other jobs in the same tick or the next tick (Task 5).
5. A template agreed after this week's slot does not make an instance for that slot (Task 3).

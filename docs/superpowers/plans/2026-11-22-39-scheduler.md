# Scheduler Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Issue:** [#39 Scheduler: scheduled instances, expiry, catch-up on boot](https://github.com/SlatinskyJ/taskmaster/issues/39)

**Goal:** In-process jobs that make scheduled instances of agreed templates, expire deadline instances after their grace window, and roll periods, all idempotent and caught up on boot after downtime.

**Architecture:** One scheduler (`src/server/scheduler/`) runs a list of jobs once at boot and then every minute on a `croner` tick in Europe/Prague. Each job is a plain function `(at: Date) => void` over the DB that does what is due at `at` and nothing when nothing is due, so running it twice, late, or after a restart is safe. Three jobs: periods (the existing `rollPeriods`, taking over the period roller's loop), expiry (a new lifecycle step `expireTask` next to the other task steps, over the domain's existing `expireItem`), scheduled instances (new domain slot rules plus a small table that remembers each template's last handled slot). The roller's own loop (`src/server/periods/roller.ts`) is deleted.

**Tech Stack:** TanStack Start (Nitro plugin), Drizzle + SQLite, `croner` 10.0.1 (new dependency, spec §11), Vitest with fake timers.

**Spec:** `docs/superpowers/specs/2026-11-16-taskmaster-design.md` §5.3 (origin 1, deadline + grace, the no-duplicate [call]), §5.6 (expired), §5.8 (period roll), §5.10 (audit), §11 (Scheduler [call]).

**Stack:** on [#187 Instances on demand and self-logged chores](https://github.com/SlatinskyJ/taskmaster/pull/187) (instance rows, `instanceDeadline`, `origin 'scheduled'`, the Prošlo group). Base branch `38-instances-and-log`; added to #187's GitHub stack when the PR opens.

**Size:** about 380 changed lines without tests, the migration and generated files: domain 70, schema 15, scheduled instances 90, expiry 40 (lifecycle step + job), scheduler 65, plugin 15, rows and strings 25, demo 45, `package.json` 1. Under the 400 mark.

## Global Constraints

- Prague wall-clock maths only through `src/domain/dates.ts` (DST rules there: a wall time in the spring gap moves forward, a doubled one resolves to the second occurrence); store UTC with `toIsoUtc`.
- `src/domain/` stays framework-free.
- Every state change writes its audit entry in the same transaction (`writeAudit`), actor `{ kind: 'system' }`, entity type `task` for instance rows (rule from #38, in `src/server/audit/README.md`).
- Never edit a committed migration: add one with `pnpm db:generate --name scheduler`. Track B's open PRs #186 (`0018_period_settings`) and #191 (`0019_period_proposals`) and #187 (`0018_instances`) take the same numbers; whichever lands later regenerates its unmerged migration with the next free number (never edits a merged one). This plan calls it `0019_scheduler` for short.
- A job never throws out of the scheduler: a failure is logged with the job name and the next tick tries again. Inside the expiry and instances jobs, each row / template is caught on its own: its failure is logged with its id and the job goes on with the next one.
- Czech UI text only in `src/lib/strings.ts`.
- Production switches stay off; nothing here turns `recurring` on (`src/server/features/README.md`). The scheduler runs regardless of the switch: with the switch off no template can be agreed in the UI, so there is nothing to schedule.

## Rulings (all go into the PR brief)

1. **One tick per minute** (`'* * * * *'`, zone Europe/Prague, `protect: true` so ticks never overlap, `unref: true` so the timer doesn't hold the process). Every job checks the DB on each tick instead of each one computing its own next wake time. Why: schedules, deadlines and the period end live in the DB and change when people act ("+ Teď", a template agreed, a meeting settles); a fixed tick needs no wake-up calls from those actions. Cost: a slot or an expiry happens up to a minute late; the domain already refuses a completion after grace (`past_grace`), so a late status flip changes no points. A tick is a handful of indexed queries. Each tick reads `now()` afresh.
2. **Boot catch-up = the first tick, run at once** when the scheduler starts (before croner's first minute), in job order periods → expiry → instances. Periods first, so an instance made by the catch-up falls after any roll; expiry before instances, so the no-duplicate check (ruling 5) does not count an instance that is about to expire. The scheduler logs `[scheduler] started: periods, expiry, instances` once.
3. **A slot** is a moment a template's schedule says an instance appears: one of `schedule.days` at `schedule.time`, or at the start of the Prague day when `time` is null (the #37 [call]). Only slots at or after the template's `agreedAt` count (`slot >= agreedAt`): a template agreed Tuesday 19:00 with "Tuesday 18:00" first appears next Tuesday.
4. **Missed slots after downtime: only the latest one per template; if its grace has already ended, it is made and expired in the same tick, both logged, no points** (decision card to Jakub in the project thread, this is the recommended option; spec §5.3 "after the grace window the instance expires; no points, logged" with "appears" read as the slot). Older missed slots are not made. If Jakub picks another option the plan is updated before the build: "every missed one" walks every slot after the last handled one, oldest first, each made (and expired when past grace); "due from restart" makes the latest one with `instanceDeadline(rule, at)` and never expires it at birth.
5. **No-duplicate [call] (spec §5.3):** for a template without a deadline, the slot makes no instance while an instance of the same template, of any origin, is still `open` or `reserved`. A `done_unconfirmed` one does not block (it is done; if a parent then rejects it, two open instances can exist, accepted and named in the brief). The slot still counts as handled, so finishing the old instance later does not make the skipped one appear late.
6. **Last handled slot** is stored in a new table `template_slots (template_id PK → templates.id, last_slot_at TEXT NOT NULL)`, written in the same transaction as the instance (or as the decision to skip). It is scheduler bookkeeping, not a family-visible state change, so it writes no audit entry; what the family sees (an instance born, expired, or none) is logged through `instance.created` / `instance.expired`. Never deleted, like the rest.
7. **The slot rules live in the domain:** `slotOutcome(input) → 'none' | 'skip' | 'make'` in `src/domain/templates.ts` decides from `{ slot, agreedAt, lastSlotAt, hasOpenInstance, deadline, at }`; the server only loads the inputs and writes the result (Task 1).
8. **A scheduled instance** is born like "+ Teď" (#38): `tasks` row with `origin 'scheduled'`, title, score and approval flag copied from the template at that moment, due time `instanceDeadline(rule, slot)` (from the slot: a tick a minute or an hour late keeps the due time), `created_by` = the template's creator (the column is NOT NULL; the audit actor says it was the system), `created_at` = the slot (when it appeared; the audit entry's `at` is the tick). Audit `instance.created`, actor system, `after` as for on-demand plus `slotAt`.
9. **Expiry is a task lifecycle step:** `expireTask(db, taskId, now)` in `src/server/tasks/lifecycle.ts` goes through `runStep` (which learns to take a system actor) with `expireItem`, so the `instance.expired` entry has the same `before`/`after` shape (`accepted`, `closed`) as every other step and gets `discardStaleChange` like them. The job selects `open`/`reserved` rows with `grace_ends_at <= at` and calls it per id; a reservation is dropped with it. One transaction per row.
10. **The period roller's loop goes away;** its job is `rollPeriods(db, at, defaults())` each tick, where `defaults` is passed in by the boot plugin: `() => DEFAULT_PERIOD_DEFAULTS` on this branch today; once Track B's [#186](https://github.com/SlatinskyJ/taskmaster/pull/186) is in the base, `() => getPeriodDefaults(db)` read per tick (an admin's save applies at the next roll), and the job keeps #186's log line with each started period's levels. #191's `rollPeriods` also applies agreed proposals; the job only calls `rollPeriods` (agreed with that thread). `startPeriodRoller`, `roller.ts` and `roller.test.ts` are deleted; their behaviours (catch up at boot, roll at cutoff, log new periods, survive a failure) move to the scheduler and job tests.
11. **Row text for a scheduled instance without a deadline:** "podle rozvrhu · út 18:00" (`cs.instances.scheduledAt(weekday, time)`), from `createdAt` (= the slot), like "na vyžádání · 15:20". With a deadline the due text wins, as for on-demand. History: `instance.expired` → "prošlo" (`cs.history.expired`); a scheduled `instance.created` (no person) → "přidáno podle rozvrhu za {n} b" (`cs.history.scheduledCreated`).
12. **`croner` 10.0.1** (Feb 2026, the `hexagon/croner` package, pure JS, no install scripts), pinned exactly. 11.x is newer than a month; 10.0.1 has what we use (`timezone`, `protect`, `unref`).

## Review Focus

1. A schedule time inside the spring DST gap (02:30 on 29 March 2026) or the doubled hour (02:30 on 25 October 2026): one slot that day, at the instant `fromPragueWallTime` gives, never two and never none (Task 1).
2. A restart in the same minute as a slot, or two ticks for the same slot, makes exactly one instance, for a template with and without a deadline (Task 3).
3. A tick exactly at `grace_ends_at` expires the row (half-open, as `pastGrace`), a tick one millisecond before does not (Task 4).
4. A failing job, row or template does not stop the others in the same tick or the next tick (Tasks 3, 4, 5).
5. A template agreed after this week's slot does not make an instance for that slot; agreed exactly at the slot instant, it does (Tasks 1, 3).

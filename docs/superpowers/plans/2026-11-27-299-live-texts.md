# Live change banner, PR 3: event texts, one change per request, open at once — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task (CLAUDE.md PR flow step 3). Steps use checkbox (`- [ ]`) syntax for tracking.

**Issue:** [#299 Live change banner](https://github.com/SlatinskyJ/taskmaster/issues/299), PR 3 of 4 (server only; PR 4 is the client and the banner). Also closes [#304 Live changes: two saves in one tick can share a change](https://github.com/SlatinskyJ/taskmaster/issues/304) and [#309 Live changes: a stream reports open only at the first heartbeat](https://github.com/SlatinskyJ/taskmaster/issues/309), and carries the follow-ups PR 2's judges left ([#306](https://github.com/SlatinskyJ/taskmaster/pull/306)).

**Goal:** every live event carries its Czech sentence, built for the stream's viewer; a change is one server request; a stream is open the moment it answers.

**Architecture:** a new `src/server/live/text.ts` turns one audit entry into `"<actor> · <phrase>[ · <title>]"` for one viewer, reusing `historyText` for task and chore actions and new `cs.live` phrases for the rest; the hub adds it per stream (live and catch-up). `writeAudit` groups by an AsyncLocalStorage scope that a request middleware opens per request, with today's microtask as the fallback outside a request (the scheduler); the hub keeps the origin tab per change. The stream writes `: open` first.

**Tech Stack:** TypeScript, TanStack Start (request middleware), better-sqlite3 + Drizzle, `node:async_hooks`, Vitest, Playwright.

**Spec:** `docs/superpowers/specs/2026-11-26-live-changes-design.md` ("The event", "One change = one action of a person", "Connection and limits", "Own changes"); `src/server/live/README.md`; `src/server/audit/README.md` ("Changes").

## Global Constraints

- Czech text only in `src/lib/strings.ts`; code, identifiers, logs in English.
- An event never carries `before` / `after`; only values the viewer's screen could load (design "The event"; audit README).
- A title (and any score in the phrase) only when the viewer may load the entity, decided by that entity's own visibility function, not a copy of its rule; otherwise the fallback `"<actor> · změna"` (`cs.history.other`).
- A taker gets the same fallback for every `user.*` entry, whatever changed (Security judge, PR 2).
- Separator ` · ` (design example "Táta · domluveno za 8 b · Vynést koš").
- `TOPIC_LIMIT` 50, `HEARTBEAT_MS` 25 s, `STREAMS_PER_SESSION` 3, `STREAMS_TOTAL` 50, `CATCH_UP_LIMIT` 100: unchanged.
- `src/domain/` untouched. No schema change, no migration, no new dependency.
- Behind `liveChanges` as today; no visible screen change in this PR (no `preview` label).

## Decisions for the judges (no spec gap; the design leaves them to the builder)

1. **Actor word.** A user: their `displayName`; the viewer himself (another tab or phone of his): `cs.live.you` = `Ty`; the system (scheduler, bootstrap): `cs.live.system` = `Podle rozvrhu` (design: "the scheduler as actor [call]"). UX judge reviews the words.
2. **Which entities have a title:** `task` (incl. copies) and `template` only, via `taskDetailHandler` / `templateDetailHandler` (null or `ForbiddenError` → no title). Every other action has a sentence without a title. The title is the entity's current one.
3. **Fallback for a task/chore the viewer may not load:** `"<actor> · změna"`, dropping the phrase too (its score is the entity's data).
4. **Taker + `user.*`:** `"<actor> · změna"`. After Task 3 a taker gets `user.*` only through `templates:proposed` on a role or active change, which only an admin (or the bootstrap) writes, so the actor is not telling.
5. **A change now spans awaits** (one request). Its later entries can land in a later flush; the hub remembers the last `CHANGE_MEMORY` = 256 changes (origin tab, streams already sent) so a stream gets each change once. A continuation after 256 newer changes, or after a catch-up that already sent it, may count once more: over-firing, accepted (design "Topics").
6. **Cost:** a title costs one detail read per (entity, viewer) per flush, cached within the flush, only for streams the change already matched. The design's "the hub only matches strings" is loosened by exactly this (needed for "a title only when the viewer may load the entity"). Architecture judge: say if you want a lighter check instead.
7. `text.ts` imports `historyText` from `~/components/tasks/historyText` (framework-free, imports only `cs` and dates), so the task's Historie and the banner share one wording. No server module imports from `~/components` today; the alternative is moving `historyText` to `src/lib/` (more churn). Architecture judge decides in round 1.

## Review Focus

1. A taker whose stream holds `templates:proposed` while a chore is proposed and hidden from him (`choreBidding` and `openRows` off): the event must carry no title and no score. Test in Task 2 (`a proposed chore a taker cannot load: fallback`).
2. The admin with `disputes` off on a task change he receives through `people` / `points:<id>`: `taskDetailHandler` throws `ForbiddenError`; the text falls back, the flush does not throw. Test in Task 2.
3. A task or template deleted or never existing (entity id gone): no title, fallback, no throw. Test in Task 2.
4. Two saves from two tabs resolved in the same tick: each tab is skipped only for its own change, the other gets it (issue #304). Test in Task 4.
5. A stream with no catch-up: the first bytes arrive before any heartbeat (issue #309). Unit test in Task 5, timing in the e2e of Task 6.

- A phrase that names a score (`historyText` would print `0 b` for none) and the entry has no integer `after.score` → fallback.
- Title null (handler null, `ForbiddenError`, entity gone, non-numeric id) → fallback `actor + sep + cs.history.other`. Any other throw propagates (the hub catches, Task 4).
- Other actions: `actor + sep + <cs.live phrase>`, no title. `MAPPED[...] === 'none'` actions are `'none'` here too and return the fallback (they never reach a stream).

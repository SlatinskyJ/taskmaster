# Demo screens Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** On the public demo (`TASKMASTER_ENV=demo`) the login page offers four one-tap accounts
and a link to `/dev/multi`, every screen shows a demo marker, every page carries `noindex`, the
locked controls are shown disabled with a short Czech note, and a `demo_locked` refusal from the
server shows a Czech message. Nothing changes outside the demo. Issue #328 (epic #322).

**Architecture:** The client learns it is on the demo from one new public server function
`getIsDemoFn` (a yes/no about the deployment, like `getDevPagesAllowed`), cached for the page's
life in the browser. The root route's `beforeLoad` puts it in the router context as `demo`, so
every route (login, `_app`, dev pages) reads `context.demo`; the root `head` adds the robots meta
from it and the root document renders the marker from it. The one-tap buttons call the existing
`loginFn` with the public demo password, so they go through the normal login and the demo's
per-IP attempt cap from #330; no new auth path. Locked screens take a `locked` prop; the shared
helper `demoLockedMessage(error)` turns a `demo_locked` refusal into Czech text at each catch.

**Tech Stack:** TanStack Start / Router (root `beforeLoad`, `head`), React, Tailwind, Vitest
(static markup), Playwright.

**Spec:** `docs/superpowers/specs/2026-11-27-demo-environment-design.md`: Goals "Login page lists
the accounts", "Demo marker, always visible", "Demo lock ... their screens show the controls
disabled", "Search engines kept out"; "Left to the builder" (Czech texts, how the client learns
it is on the demo, the PR split). Server side is #330 (`src/server/env/demo.ts`,
`src/server/demo/lock.ts`, `src/server/auth/README.md`).

**Size:** about 230 changed lines outside tests (strings ~20, `src/lib/demo*.ts` ~45, server fn
+ guard list ~12, root route ~25, marker ~15, login + `DemoAccounts` ~70, locked controls ~40,
README ~5). One PR, no stack: the split the design suggested ("login page + marker + noindex")
already is this PR, and the three parts share one source of the demo flag. Not a small PR: it
touches the Czech strings module and `PUBLIC_SERVER_FNS` (protected areas).

**Panel:** plan phase Architecture, Tests, Security (a new entry in `PUBLIC_SERVER_FNS`, the
role-check list). Code phase adds UX.

## Decisions where the design left a choice

1. **How the client learns it is on the demo:** `getIsDemoFn` in `src/server/env/functions.ts`,
   handler `isDemo(process.env)`, returns a plain `boolean`; public, listed in
   `PUBLIC_SERVER_FNS` with the reason "the login screen and the app shell ask whether this is
   the public demo; a yes/no about the deployment". Cached in the browser with `clientCache`
   for the page's life (`Infinity`): the env never changes while a server runs, a reload asks
   again. The server render always asks (clientCache never caches on the server), so the SSR
   HTML already has the marker and the robots meta. A failed call counts as "not the demo"
   for that one navigation, and the catch sits outside the cache
   (`loadIsDemo = () => cached().catch(() => false)`), so a failure is never kept and the next
   navigation asks again: a page must not break over the marker; the server lock still holds.
   Blast radius (goes into the brief): every route now awaits `loadIsDemo` in the root
   `beforeLoad` (one server call per SSR request, cached in the browser), and every route's
   context gains `demo`.
2. **The one-tap buttons use `loginFn` with `DEMO_PASSWORD`**, not a new server function. The
   password is public by design (all four demo accounts are public; it is in the repo and in
   `CLAUDE.md`). It moves to a framework-free `src/lib/demoAccounts.ts` next to `DEMO_LOGINS`
   (moved from `src/lib/multiLayout.ts`). One home, no re-exports: every importer
   (`src/lib/multiLayout.ts` users, `src/server/demo/seed.ts`, `src/server/demo/index.ts`,
   `src/server/auth/frameLogin.ts`, `seed.test.ts`) imports from `~/lib/demoAccounts`, so seed
   and buttons cannot drift. The same file holds `DEMO_LOCKED = 'demo_locked'`, used by both
   `DemoLockedError` (`src/server/demo/lock.ts`) and `demoLockedMessage`. It ships in every client bundle;
   that opens nothing in production, where `ADMIN_PASSWORD` is set and the demo seed refuses,
   so no account has that password. This keeps auth code untouched: same rate limits, audit and
   frame handling (a button pressed inside a `/dev/multi` frame keeps its token, as the form does).
3. **Czech texts** (`cs.demo` in `src/lib/strings.ts`; UX judge may reword):
   - marker: `Demo · každou noc se vše smaže`
   - section above the buttons: `Vyzkoušej bez hesla jako`
   - buttons: the existing `cs.devMulti.users` (`Admin`, `Táta`, `Starší`, `Mladší`), moved to
     `cs.demo.users` and used by both (`cs.devMulti.users` becomes a reference to it)
   - link: `Více zařízení`, its hint below: `Víc lidí vedle sebe, jako telefony na stole`
   - note under a locked control: `V demu zamčeno, ať to vydrží i dalším návštěvníkům.`
   - the lock's error: `V demu tohle nejde. Zamčeno, ať to vydrží i dalším.`
4. **Marker:** one `<p data-slot="demo-marker">` first in `<body>` (in `RootDocument`, so login,
   app, dev pages and each `/dev/multi` frame get it), `sticky top-0 z-40` (dialogs and sheets
   are `z-50` and cover it; the bottom bar is `z-40` at the bottom), `pointer-events-none`,
   `bg-accent2 text-ink text-center text-xs font-extrabold py-1`, text wraps at 360 px rather than cut.
   Not focusable, no landmark; its text is read as normal text.
5. **noindex:** `<meta name="robots" content="noindex, nofollow">` from the root `head` on the
   demo. No `X-Robots-Tag` header: the SSR HTML carries the meta on every page, including
   `/dev/multi` (its route is `ssr: false`, the root still renders on the server).
6. **Locked controls:** Správa → Funkce: every switch row `disabled`, the lock note replaces the
   card's usual note. Správa → people: `Přidat člověka` disabled with the note under it; the
   rows still open the sheet, so a visitor sees the form, but its fieldset is `disabled` (fields,
   `Uložit`, `Obnovit heslo`) with the note at its top. Profil → Heslo: the row disabled, the
   note under it; the sheet never opens. Passkey controls are already hidden on the demo
   (passkeys off, #330).
7. **Lock error:** each catch on the five locked calls maps `demo_locked` to the Czech error,
   else keeps today's message. That is the second wall for a page whose controls were not
   disabled (a future control, a stale bundle).

## Global Constraints

- Every demo-only path reads `demo` from the router context, which comes only from `isDemo`
  (`TASKMASTER_ENV === 'demo'` and no `ADMIN_PASSWORD`). Previews (`preview`) and production
  show none of it.
- Czech UI text only in `src/lib/strings.ts`; identifiers English.
- Never a real host name; examples use `taskmaster.example.cz`.
- Component tests render static markup only; interactions in e2e.
- No state change, so no audit entries in this PR.
- The `ADMIN_PASSWORD` guards in `src/server/demo/seed.ts` and `src/server/auth/frameLogin.ts`
  stay untouched (Security): they are why the public `DEMO_PASSWORD` in the bundle opens
  nothing in production.

## Review Focus

1. A tap on a demo button while another login is running: all four buttons and the form's submit
   are disabled until it ends; the tapped one shows `aria-busy`. Test in Task 2 (static markup
   with `busy`).
2. A demo button fails (rate limit after 60 attempts, network): the same error line as the form
   (`cs.login.rateLimited` / `cs.login.failed`), buttons usable again (`busyLogin` reset). e2e
   in Task 2: the login POST fails once via `page.route`, then a second tap logs in.
3. A preview or production page: no marker, no robots meta, no buttons, no locked note. e2e in
   Task 1 (marker, meta) and Task 2 (buttons, link) on the preview `fonts` suite; static markup
   tests with `demo: false` / `locked: false`.
4. A visitor re-enables a disabled control in DevTools: the server refuses and the Czech lock
   error shows. e2e in Task 3 through the person sheet's `<fieldset>` (React drops clicks on a
   button whose own `disabled` prop is true even after the attribute is removed, so the switch
   and Heslo rows cannot be driven that way).
5. The marker over a sheet or dialog: they stay above it (`z-50`). Covered by the code-phase
   screenshots of the locked person sheet on the demo.

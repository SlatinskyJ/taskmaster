# Periods: storage, auto roll at cutoff, lock on start — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Issue:** [#42 Periods: storage, auto roll at cutoff, lock on start](https://github.com/SlatinskyJ/taskmaster/issues/42)

**Goal:** periods are stored in the DB, roll over by themselves at the cutoff (catching up after downtime), end early when a settlement ends them, and the points query uses the running period's levels.

**Architecture:** the §5.8 rules stay in `src/domain/periods.ts` (pure; already holds the chain maths). This PR changes the default cutoff to Sunday 23:59, adds the early end that settling causes, and adds DB storage plus a small in-process roller in `src/server/periods/`. The scheduler (#39) is deferred for launch (Jakub, planning thread 2026-11-21: recurring chores are hidden and #39 waits; #42 brings "its own small roll-over job that catches up on boot"), so the roller is its own `setTimeout` loop started by the boot plugin, and #39 takes it over later (noted on #39); it runs once at boot (catch-up) and then wakes at the running period's end (at most 1 h apart). No screen, no server function: #44 (meeting) and #45 (week view) are the consumers.

**Tech Stack:** TypeScript strict, Drizzle + better-sqlite3, Vitest (fake timers), Nitro boot plugin.

**Spec:** `docs/superpowers/specs/2026-11-16-taskmaster-design.md` §5.8 (periods, as changed by PR #161), §5.5 (attribution by `completed_at`), §5.10 (audit).

**Size:** about 340 changed lines without tests and the generated migration (domain ~60, schema ~45, server module ~130, roller ~50, plugin + audit list ~10). One PR: the roller is useless without storage and storage without the roller has nothing to test end to end.

**Judges:** Rules, Architecture, Tests, Ops (boot plugin starts the roller).

## Global Constraints

- Defaults (spec §5.8, decided by Jakub 2026-11-21): length **7 days**, cutoff **Sunday 23:59 Europe/Prague**, levels **lower 50, upper 100**. No admin settings UI and no settings table in this PR (#47 is out of scope for launch).
- A period is half-open `[startsAt, end)`, `end = endedAt ?? cutoffAt`. An instant exactly at the end belongs to the next period.
- "Settling ends the period": confirming the settlement ends the running period at that moment; the next one starts then, its cutoff from its start and the default length (Sunday 20:00 → next Sunday 23:59).
- If no settlement happens by the cutoff, the next period starts at the cutoff ([call] §5.8).
- Once started, a period's cutoff and levels never change. `ended_at` is the only column ever updated, once, from null.
- Store UTC via `toIsoUtc`; all Prague maths through `src/domain/dates.ts`.
- Every state change (period created, period ended) writes its audit entry in the same transaction. Roller actor is `{ kind: 'system' }`.
- English code and logs; no Czech strings in this PR.
- Never put a production host name anywhere (use `taskmaster.example.cz` if needed).

## Rulings (spec silent; recorded in the PR brief)

1. **First period starts at the first roll** (boot of the first server with this code), with the default cutoff nearest `start + 7 days`. Deployed from Sat 21 to about Thu 26 Nov, it ends Sun 29 Nov 23:59; deployed later it ends Sun 6 Dec 23:59, and the meeting on 29 Nov ends it early anyway (settling ends the period). Completions before it belong to no period: they still count in the running total (#40), they just don't show in a week's list.
2. **A per-period proposal is keyed on the period it follows (`afterPeriodId`), not on a start instant.** With early ends the next period's real start is unknown in advance. A proposal is open while the period it follows is running; once that period has ended (early or at the cutoff) the proposal can no longer be approved and a pending one lapses; an agreed one applies to the period that starts after it, whenever that is. #43 stores proposals and owns wiring them into both start paths (roller and `endRunningPeriod`), lapsing pending ones at the actual start, and refusing approvals after it; this PR changes the domain functions and passes `null` on both paths (named in the `src/server/periods/` module header).
3. **`canSettle` becomes "started and not ended early".** The spec now allows settling the running period before its cutoff and a period ended at its cutoff any time after. Double settlement of a cutoff-ended period is guarded by settlement records in #44, not here.
4. **Defaults stay code constants** (`DEFAULT_PERIOD_DEFAULTS`). The server functions take `defaults` as a **required** parameter (no default value), so when #43/#47 add stored settings the type checker points at every caller. Settings storage moves to #43 (it needs it first) / #47; noted on #42 in the brief.
5. **Hand-off to #44:** `endRunningPeriod` takes the id of the period being settled and refuses (`not_running`) unless exactly that period is still running, checked inside #44's transaction. A retried confirm, or a meeting confirmed after the roller already rolled at 23:59, can never end the new period.

## Review Focus

1. **Server down over the cutoff (or several).** Boot after a long downtime creates every missed period in order, each with its own default cutoff, no gaps or overlaps, and is a no-op on the second run. → Task 3 test `catches up several missed cutoffs in one roll`, `second roll is a no-op`.
2. **A completion at the exact cutoff instant / exact early-end instant.** It belongs to the next period. → Task 1 test `periodAt: endedAt instant belongs to the next period`; Task 3 test `periodAtInstant at the cutoff instant`.
3. **Settling at 23:58 on the cutoff Sunday, or on Saturday.** The next period still ends on a Sunday 23:59 a week (or 8 days) later, never the same night. → Task 1 tests `endPeriodEarly at Sunday 23:58 → next Sunday 23:59`, `endPeriodEarly on Saturday 20:00 → Sunday 23:59 eight days later`.
4. **Roller error or a timer wake slightly before the cutoff.** A thrown error is logged and the loop keeps going; an early wake reschedules instead of skipping the roll. → Task 4 tests `keeps running after a failed roll`, `an early wake rolls at the next wake`.
5. **DST weeks with the 23:59 cutoff.** Autumn and spring weeks end at 23:59 wall time (169 h / 167 h). → Task 1 tests on the 23:59 defaults.

**Interfaces:**
- Consumes: `rollPeriods`, `currentPeriod`, `periodEnd`.
- Produces: `startPeriodRoller(db: Db, defaults: PeriodDefaults, opts?: { now?: () => Date; maxDelayMs?: number; retryDelayMs?: number; log?: Pick<Console, 'info' | 'error'> }): { stop(): void }`
  - option defaults: `now = () => new Date()`, `maxDelayMs = 3_600_000`, `retryDelayMs = 60_000`, `log = console`.
  - On start: the first tick runs at once (boot catch-up) through the same catch-and-log path as later ticks, so a failed boot roll never stops the server; it logs `[periods] running period ends <ISO>` and, for each created period, `[periods] started <startsAt ISO> → <cutoffAt ISO>`.
  - Then `setTimeout(tick, clamp(periodEnd(current) − now, 0, maxDelayMs))`; each tick rolls and reschedules the same way. A thrown error → `log.error('[periods] roll failed', err)` and the next tick in `retryDelayMs`. The timer is `unref()`ed. `stop()` clears it.

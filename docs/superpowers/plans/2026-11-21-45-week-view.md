# Week view and settlement history Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Týden tab shows takers and givers this week (dates, levels, confirmed and pending points, this week's items) and past weeks (settlement records), issue [#45](https://github.com/SlatinskyJ/taskmaster/issues/45).

**Architecture:** One read, `getWeek(db, viewer, now)` in `src/server/settlement/week.ts`, built from the existing pieces: `currentPeriod` (#42), `ledgerEntries` + domain `runningTotal` (#44), the `settlements` and `periods` tables. One server function `getWeekFn` (taker and giver) passes the signed-in user as the viewer; the server filters to the viewer's own data for a taker. The route `/_app/tyden` renders `WeekScreen` with two tabs (Tento týden / Historie). The demo seed gains one settled past week so Historie is never empty in a preview.

**Tech Stack:** TanStack Start/Router, React, Drizzle + better-sqlite3, Vitest (node env, `renderToStaticMarkup`), Playwright e2e.

**Spec:** `docs/superpowers/specs/2026-11-16-taskmaster-design.md` §5.7, §5.8, §5.9, §5.11; UI doc `docs/superpowers/specs/2026-11-16-taskmaster-ui-design.md` §5 (Tabs), §6 (nav), §7.1 TWeek.

Stacked on [#175 Weekly meeting: clear pending, settle, plan](https://github.com/SlatinskyJ/taskmaster/pull/175) (branch `44-meeting-screens`), stack 169.

- All Prague wall-clock maths through `src/domain/dates.ts`; dates leave the server as UTC ISO (`toIsoUtc`).

- §5.9: settlements are final; nothing on this screen edits them.

- Screens work at 360 px with long task names.

## Rulings (where the spec is silent; recorded in the brief)

1. **[call] Who sees what.** A taker sees only his own card and his own history rows; a giver sees every active taker. The filter is on the server (`getWeek`), not in the screen. The admin has no Týden tab (nav already: taker, giver).
2. **This week's items** = the taker's tasks completed since the running period started (confirmed or waiting), plus any still-waiting completion from before the start (it counts in pending, so it is listed). Newest first. A rejected completion is not listed: rejecting returns the task to reserved/open (§5.5), so there is no item left to show. Rejections with "Rozporovat" come with #46 if Jakub wants them.
3. **"Z minula převedeno"** = the carry-over of the taker's latest settlement record, 0 when there is none. The confirmed number is the ledger running total (same as the meeting), so a late meeting (last week not settled yet) shows last week's points in it too, as the meeting would settle them.
4. **History** = settled weeks only, newest first, each with its range (start to `endedAt ?? cutoffAt`), levels and one row per record. No paging: a family has ~52 weeks a year.
5. **Corrections** (#48) do not exist yet; history shows records as stored. No placeholder text.
6. **"Návrh na příští týden ›"** (TWeek mockup) belongs to #43 period proposals; not in this PR.
7. Settlement code is reused from #44: `getWeek` lives next to `getMeeting` in `src/server/settlement/`. When [#162 Points query and taker home (Domů)](https://github.com/SlatinskyJ/taskmaster/pull/162) lands, its points read and this one should agree; #172 tracks settlements in #162's points. Noted as a duty in the brief.
8. **Demo past week.** `seedDemo` first starts a week 7 days ago, does a few chores in it through the real actions, and settles it through the real `settlePeriod`; then the existing demo week runs in the new period. To call those inside the seed transaction, `rollFirstPeriod` is added to `src/server/periods/periods.ts` (the `first` branch of `rollPeriods`, taking `Tx`), and `settlePeriod` takes `Db | Tx` (drizzle runs the inner `transaction` as a savepoint).

## Review Focus

1. A taker opening Týden must never receive another taker's numbers or history, even in the loader payload. Test on `getWeek` and on `getWeekFn`'s viewer wiring.
2. Fresh database before the first period exists, or a taker with no settlement yet: the screen shows an empty state and 0 carried in, never crashes. Tests in Task 1 and Task 3.
3. A late meeting (last week ended, not settled): confirmed includes last week's confirmed points, items list shows this period's items, and a still-waiting item from last week is listed and counted in pending. Test in Task 1.
4. A long task name (`Vyluxovat celý obývák a chodbu`) and a long display name at 360 px: rows wrap, numbers stay on screen. Screenshot check in Task 5.
5. Week range in History uses the real end (`endedAt` when the meeting ended it early, else the cutoff), in Prague time. Test in Task 1 (`endedAt` set) and Task 3 (label).

```ts
export interface WeekItem {
  taskId: number
  title: string
  score: number
  status: 'confirmed' | 'done_unconfirmed'
  completedAt: string // UTC ISO
}
export interface WeekTaker {
  id: number
  name: string
  confirmed: number // ledger running total now
  pending: number // sum of the taker's done_unconfirmed scores
  carriedIn: number // carryOver of his latest settlement, else 0
  items: WeekItem[] // newest first
}
export interface HistoryRecord {
  takerId: number
  name: string
  totalBefore: number
  level: Level
  deducted: number
  carryOver: number
}
export interface HistoryWeek {
  periodId: number
  startsAt: string
  endsAt: string // endedAt ?? cutoffAt
  levels: Levels
  records: HistoryRecord[] // by taker id
}
export interface Week {
  period: { id: number; startsAt: string; cutoffAt: string; levels: Levels } | null
  takers: WeekTaker[] // by user id
  history: HistoryWeek[] // newest first
}
export interface Viewer { id: number; role: Role }
export function getWeek(db: Db | Tx, viewer: Viewer, now: Date): Week
```

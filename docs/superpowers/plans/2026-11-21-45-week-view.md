# Week view and settlement history Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The Týden tab shows takers and givers this week (dates, levels, confirmed and pending points, this week's items) and past weeks (settlement records), issue [#45](https://github.com/SlatinskyJ/taskmaster/issues/45).

**Architecture:** One read, `getWeek(db, viewer, now)` in `src/server/settlement/week.ts`, built from the existing pieces: `currentPeriod` (#42), a new per-taker `takerPointsNow` next to `ledgerEntries` (#44), the `settlements`, `periods` and `audit_log` tables (rejections). One server function `getWeekFn` (taker and giver) passes the signed-in user as the viewer; the server filters to the viewer's own data for a taker. The route `/_app/tyden` renders `WeekScreen` with two tabs (Tento týden / Historie). The demo seed gains one settled past week so Historie is never empty in a preview.

**Tech Stack:** TanStack Start/Router, React, Drizzle + better-sqlite3, Vitest (node env, `renderToStaticMarkup`), Playwright e2e.

**Spec:** `docs/superpowers/specs/2026-11-16-taskmaster-design.md` §5.7, §5.8, §5.9, §5.11; UI doc `docs/superpowers/specs/2026-11-16-taskmaster-ui-design.md` §5 (Tabs), §6 (nav), §7.1 TWeek.

**Size:** about 420 changed lines outside tests (read + rejections ~150, screen ~150, strings/helpers + move ~60, seed ~60). Slightly over 400: the shared-helper move and the rejections are asked for by review, and splitting the read from its only screen would leave an unused read. One PR.

Stacked on [#175 Weekly meeting: clear pending, settle, plan](https://github.com/SlatinskyJ/taskmaster/pull/175) (branch `44-meeting-screens`), stack 169.

## Global Constraints

- UI labels Czech, only in `src/lib/strings.ts`; code, identifiers and tests in English.
- All Prague wall-clock maths through `src/domain/dates.ts`; dates leave the server as UTC ISO (`toIsoUtc`).
- §5.7: a taker sees confirmed (carry-over + confirmed this period) and pending separately, against lower and upper. "Givers see the same for every taker."
- §5.9: settlements are final; nothing on this screen edits them.
- §5.11: disputes are #46. This PR leaves the slot (no button).
- Read-only PR: no schema change, no migration, no new audit action.
- Screens work at 360 px with long task names: a task title wraps (`break-words`), the points and the day stay whole on the right; a long taker name wraps above its badge.
- Tabs use the existing `TabsTrigger` (`min-h-tap`, no animation). The route has no action, so no busy state; its loader error is the app's `RouteError`, and every empty case has its own text (Task 4).
- The loader payload shape is pinned: `getWeekFn`'s result for a taker is checked key by key in Task 2 (no other taker, no user fields beyond id and name).

## Rulings (where the spec is silent; recorded in the brief)

1. **[call] Who sees what.** A taker sees only his own card and his own history rows; a giver sees every active taker. The filter is on the server (`getWeek`), not in the screen, and is default-deny: every taker only when `viewer.role === 'giver'`, otherwise only `viewer.id`. The admin has no Týden tab (nav already: taker, giver).
2. **This week's items** = the taker's tasks completed since the running period started (confirmed or waiting), plus any still-waiting completion from before the start (it counts in pending, so it is listed), plus this period's rejections of his completions. Rejecting returns the task to reserved/open (§5.5), so a rejection is read from its `task.rejected` audit entry (`at` ≥ period start, `before.completedBy` = the taker): task title, score from `before`, the giver's reason when given. Newest first by `completedAt` (a rejection by its `at`). Rozporovat on confirmed and rejected items is #46's (§5.11 lists both as locked items).
3. **"Z minula převedeno"** = the carry-over of the taker's latest settlement record (highest `settledAt`, then id), 0 when there is none. The confirmed number is the ledger running total (same as the meeting), so a late meeting (last week not settled yet) shows last week's points in it too, as the meeting would settle them.
4. **History** = settled weeks only, newest first, each with its range (start to the domain's `periodEnd`), levels and one row per record. No paging: a family has ~52 weeks a year.
5. **Corrections** (#48) do not exist yet; history shows records as stored. No placeholder text. Duty recorded on [#48](https://github.com/SlatinskyJ/taskmaster/issues/48) (comment) and in the brief: when corrections land, Týden Historie shows each next to its original.
6. **"Návrh na příští týden ›"** (TWeek mockup) belongs to #43 period proposals; not in this PR.
7. **One points helper.** `takerPointsNow(db, now): Map<takerId, { confirmed, pending }>` in `src/server/settlement/ledger.ts`: confirmed = `runningTotal(ledgerEntries(db), id)`, pending = sum of `done_unconfirmed` scores keyed by `earnerId` (as [#162 Points query and taker home (Domů)](https://github.com/SlatinskyJ/taskmaster/pull/162) keys it). `getWeek` uses only it. A comment on [#172](https://github.com/SlatinskyJ/taskmaster/issues/172) records that whichever of #162 / #177 lands second makes #162's `takerPoints` call it, so Domů and Týden cannot disagree. The taker list is `takersOf` from `meeting.ts`, exported.
   - **Shared view helpers.** `weekLabel`, `levelLabel`, `dayTime` and the level badge colours move from `components/meeting/meetingView.ts` to `src/components/period/periodView.ts`; Schůzka and Týden both import from there.
8. **Demo past week.** `seedDemo`, right after creating the users, starts a week 7 days ago with the real `rollPeriods`, does a few chores in it through the real actions, and settles it through the real `settlePeriod`; then templates and the existing demo week run in the new period, so the audit log stays in time order. `rollPeriods` and `settlePeriod` take `Db | Tx` (drizzle runs the inner `transaction` as a savepoint). No new export in `periods.ts`.
9. **No period** (`period: null`: a fresh database, or the minutes between a cutoff and the roller's tick): the header and items show `cs.week.noPeriod`, the cards still show `confirmed`/`pending` from the ledger (they don't depend on a period), history is unchanged.
10. **Looks.** Items use `TaskRow` (state chip `confirmed`, `pending` or `rejected`, points as the row shows them elsewhere, meta = day only; a rejection's meta = day · reason). The card shows numbers only through `PointsBar`'s own caption. The taker's screen title is `Můj týden`; the giver's stays `Týden`.

## Review Focus

1. A taker opening Týden must never receive another taker's numbers or history, even in the loader payload. Test on `getWeek` and on `getWeekFn`'s viewer wiring.
2. Fresh database before the first period exists, the gap between a cutoff and the roll, or a taker with no settlement yet: the screen shows an empty state and 0 carried in, never crashes, cards keep ledger numbers. Tests in Task 1 and Task 4.
3. A late meeting (last week ended, not settled): confirmed includes last week's confirmed points, items list shows this period's items, and a still-waiting item from last week is listed and counted in pending. Test in Task 1.
4. A long task name (`Vyluxovat celý obývák a chodbu`) and a long display name at 360 px: rows wrap, numbers stay on screen. Screenshot check in Task 5.
5. Week range in History uses the real end (`endedAt` when the meeting ended it early, else the cutoff), in Prague time. Test in Task 1 (`endedAt` set) and Task 3 (label).

```ts
export interface WeekItem {
  taskId: number
  title: string
  score: number
  status: 'confirmed' | 'done_unconfirmed' | 'rejected'
  /** UTC ISO: completion time; for a rejection, when it was rejected. */
  at: string
  /** Rejections only: the giver's reason, else null. */
  reason: string | null
}
export interface WeekTaker {
  id: number
  name: string
  confirmed: number // ledger running total now
  pending: number // sum of the taker's done_unconfirmed scores
  carriedIn: number // carryOver of his latest settlement, else 0
  items: WeekItem[] // newest first
}
export interface HistoryRecord {
  takerId: number
  name: string
  totalBefore: number
  level: Level
  deducted: number
  carryOver: number
}
export interface HistoryWeek {
  periodId: number
  startsAt: string
  endsAt: string // periodEnd(period)
  levels: Levels
  records: HistoryRecord[] // by taker id
}
export interface Week {
  period: { id: number; startsAt: string; cutoffAt: string; levels: Levels } | null
  takers: WeekTaker[] // by user id
  history: HistoryWeek[] // newest first
}
export interface Viewer { id: number; role: Role }
export function getWeek(db: Db | Tx, viewer: Viewer, now: Date): Week
// ledger.ts
export function takerPointsNow(db: Db | Tx): Map<number, { confirmed: number; pending: number }>
```

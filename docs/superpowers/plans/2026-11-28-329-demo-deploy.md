# Demo deploy: controller with reset, CI job — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Issue:** [#329 Deploy the demo: controller with reset, CI job](https://github.com/SlatinskyJ/taskmaster/issues/329), part of epic #322.

**Goal:** The public demo host gets the production deploy path plus a `reset` command, CI deploys it after `deploy prod`, and a host timer resets it every night at 03:00 Prague.

**Architecture:** A thin controller `deploy/demo/tm-demo` is the demo host's `deploy` login shell. It hands `deploy` and `status` to the unchanged production controller `tm-prod` (installed next to it on the demo host only) and adds `reset` itself. The production host never gets `tm-demo`, so nothing there can wipe data. A CI job `deploy demo` mirrors `deploy prod` with its own GitHub environment, Tailscale tag and secrets, and is off until the repository variable `DEMO_HOST` is set. A systemd timer on the demo host runs `tm-demo reset` nightly.

**Tech Stack:** bash, Docker Compose, systemd timer, GitHub Actions, Tailscale SSH, Vitest (runs the scripts with stub `docker`).

**Spec:** `docs/superpowers/specs/2026-11-27-demo-environment-design.md` (sections Nightly reset, Auto-deploy, Own controller, Ops outside the repo).

**Size:** about 140 lines of code and config (controller ~80, units ~20, CI job ~25, CLAUDE.md 1), plus a runbook (~110 lines of docs) and one test file. Protected area (CI, deploy), so this PR has a plan.

## Global Constraints

- No host names, IPs, users other than `deploy`, ports, tailnet names or limits in the repo (memory rule; spec: "Host, hostname, proxy and container limits live in Jakub's private notes"). Examples use `<container>` and `demo.example.cz`.
- `deploy/prod/tm-prod` is not changed. Production never gets a `reset` command (spec: "The production controller never gets a `reset` command").
- `deploy demo` runs only after `deploy prod` succeeds, never blocks or rolls back production (spec Auto-deploy).
- Demo secrets live only in the GitHub environment `demo` (deployment branches: `main` only), never as repository secrets; the demo tag cannot reach production.
- CI never changes the host; controller and units are copied in by hand (as for prod).
- English in code, comments, logs and docs.

## Review Focus

1. A reset that runs while a CI deploy is mid-way: the two must not interleave (one waits for the other).
2. A reset where the app does not come back healthy: exits 1, keeps the app log on the host, never prints logs to stdout (CI and timer logs may be read elsewhere).
3. A login-shell call with anything other than the allowed commands (`reset now`, `rm -rf /`, empty): refused, nothing runs.
4. `tm-prod reset` on the production host: refused as an unknown command (pins "prod has no reset").
5. Merging before the demo host exists: `deploy demo` is skipped while `DEMO_HOST` is unset, so `main` stays green.

### Task 1: Demo controller `tm-demo` with `reset`

**Files:**
- Create: `deploy/demo/tm-demo` (mode 0755)
- Test: `tests/tm-demo.test.ts`

**Interfaces:**
- Produces (contract with the CI job and the timer, written in the script header like `tm-prod`'s):
  - `deploy <sha7>`, `status`: `exec "$TM_PROD" <same args>` (env `TM_PROD`, default `/usr/local/bin/tm-prod`). Same exit codes and stdout as `tm-prod`.
  - `version`: one line `tm-demo <12-char sha256 of this script> tm-prod <output of "$TM_PROD" version>`.
  - `reset`: exit 0 with stdout `reset: done` when the app is healthy again; exit 1 otherwise, stderr names the log file under `~/logs/reset-<UTC stamp>.log`.
  - Anything else, or extra arguments: exit 1, stderr `unknown command '<cmd>'. Allowed: deploy, status, version, reset` (or a usage line), nothing run.
  - Login-shell form `tm-demo -c "<command>"` as in `tm-prod`.
- Env knobs (tests use them): `TM_APP_DIR` (default `/opt/taskmaster`), `TM_DATA_VOLUME` (default `taskmaster_tm-data`), `TM_PROD`, `TM_HEALTH_WAIT` (default 90 s), `TM_LOCK_WAIT` (default 300 s).

Reset steps, in this order, all under the lock:
1. Take `flock -w "$TM_LOCK_WAIT"` on `${HOME}/.tm-prod.lock`, the same file `tm-prod deploy` locks, so a reset and a deploy never overlap. Comment: keep in step with `lock()` in `deploy/prod/tm-prod`. `deploy` is not locked by `tm-demo` (tm-prod locks it itself; holding it here would deadlock).
2. `trap '' HUP PIPE` (as tm-prod: a dropped session must not stop half-way).
3. `docker compose rm -s -f taskmaster` in `TM_APP_DIR` (stops and removes the container so the volume is free).
4. `docker volume rm "$TM_DATA_VOLUME"`. Only a "no such volume" error is fine (warn, go on). Any other error (for example "volume is in use"): start the app again on the old data (`compose up -d --no-deps taskmaster`), stderr `reset failed: could not remove the data volume; app restarted on the old data`, exit 1.
5. `docker compose up -d --no-deps taskmaster` (Compose recreates the volume; the image stays pinned by `compose.override.yaml`; the server migrates and seeds the empty DB on boot).
6. Poll `"$TM_PROD" status` once a second up to `TM_HEALTH_WAIT` for a line that is exactly `health: healthy` (whole-line match, so `health: unhealthy` never counts). On timeout: `docker logs --tail 200 <container>` into the log file, exit 1.

Each test makes a temp dir with a stub `docker` (appends its argv to `calls.log`; `docker compose ps -q` prints `abc`; `docker logs` prints `app log line`) and a stub `tm-prod` (appends argv; `status` prints `image: x` and `health: $STUB_HEALTH`), puts the stub dir first on `PATH`, sets `HOME` to the temp dir, and runs `bash deploy/demo/tm-demo` with `spawnSync`.
  - `reset recreates the data volume and waits for healthy`: `STUB_HEALTH=healthy`; exit 0, stdout `reset: done`; docker calls in order contain `compose rm -s -f taskmaster`, then `volume rm taskmaster_tm-data`, then `compose up -d --no-deps taskmaster`.
  - `reset uses TM_DATA_VOLUME`: `TM_DATA_VOLUME=demo_vol` → `volume rm demo_vol`.
  - `reset fails and keeps the log on the host when the app stays unhealthy` (`it.each` over `STUB_HEALTH=starting` and `STUB_HEALTH=unhealthy`), `TM_HEALTH_WAIT=2`; exit 1; stdout has no `reset: done` and no `app log line`; stderr contains `logs/reset-`; that file contains `app log line`.
  - `reset goes on when the volume is already gone`: stub `docker volume rm` prints `Error: No such volume: taskmaster_tm-data` and exits 1; `STUB_HEALTH=healthy`; exit 0, `reset: done`, stderr has a warning, `compose up` was called.

  - `reset with the real tm-prod reads its health line`: `TM_PROD=deploy/prod/tm-prod`, stub `docker inspect` prints `healthy`; exit 0, `reset: done` (pins the `status` line format `tm-demo` parses).
  - Lock helper: a child `flock "$HOME/.tm-prod.lock" -c 'touch $HOME/locked; sleep N'`; the test waits until `$HOME/locked` exists before it starts `tm-demo` (no race).
  - `reset gives up when a deploy holds the lock too long`: child holds 5 s, `TM_LOCK_WAIT=1`; exit 1, stderr mentions the lock, `calls.log` has no docker call.
  - `reset waits for a deploy to finish, then runs`: child holds 2 s, `TM_LOCK_WAIT=10`; exit 0, `reset: done`, and the run took at least 1.5 s (so `flock -n` fails this test).
  - `tm-demo and tm-prod lock the same file`: both script texts contain `${HOME}/.tm-prod.lock`.
  - `deploy and status go to tm-prod unchanged`: `deploy abc1234` → tm-prod stub got `deploy abc1234`; `-c "status"` → stub got `status`; exit codes passed through (stub exits 3 → 3).
  - `version names both scripts`: stdout is `tm-demo <first 12 hex of sha256(deploy/demo/tm-demo)> tm-prod <stub output>`, the hash computed in the test with `node:crypto`.
  - `refuses anything else`: each of `reset now`, `rm -rf /`, ``, `-c "reset; rm -rf /"` → exit 1, no stub call at all.
  - `tm-prod has no reset`: run the real `deploy/prod/tm-prod reset` with the stub docker → exit 1, stderr contains `unknown command 'reset'`, no docker call.
